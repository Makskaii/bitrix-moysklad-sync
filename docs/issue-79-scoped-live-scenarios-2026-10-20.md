# Issue #79 scoped live scenarios (2026-10-20)

Status: **plan only; every live scenario below is NOT RUN**. This matrix is a controlled acceptance plan, not evidence of provider delivery, permission, deployment, or runtime correctness. It supersedes the live-test portions of the historical [Issue #60 live-test plan](issue-60-live-test-plan.md) and [combined #55/#57/#61 acceptance matrix](acceptance-matrix-55-57-61.md) for current #79 work. Their historical evidence remains intact.

## Authority and isolation boundary

- The only permitted live scope is named synthetic test records created for one unique run ID, with a restricted manifest containing each exact native ID, direction, creation boundary, and only required read-only dependencies. Pin the Bitrix24 portal origin, verified integration principal ID, and MoySklad account ID; abort on any mismatch.
- Use a newly provisioned, isolated server PostgreSQL database **and** schema dedicated to that run. Production PostgreSQL and its existing queue are out of scope. Keep primary service mode **OFF** throughout preparation and deployment. Do not replay or mutate existing production queue rows.
- Before intake, prove that controlled-mode isolation is active end-to-end: unmatched/unmanifested events cannot reach a processor or external write. If exact native-ID admission cannot be demonstrated, stop. Keep existing authentication, TLS, provider namespace, webhook secret handling, URL/redirect validation, and external-write guards intact; no test-only bypasses.
- Assign one named operator/actor and a distinct independent stop authority before the window. The actor alone performs the approved UI/API actions. Root records their names, window, exact SHA, settings revision, scope switches, and stop method in the run record; this plan does not name people or confer new authority.
- Callback delivery must originate from the provider's configured webhook mechanism and be correlated to the synthetic manifest record. Manually posting to our HTTP route, replaying a captured request, or faking a callback is not proof of real delivery. The preflight found Bitrix event-registry visibility unverified (`event.get` returned `WRONG_AUTH_TYPE`) and all nine MoySklad hooks targeting the current service host disabled; no callback delivery was tested. The exact hooks/permissions and callback reachability must be resolved through approved setup before these scenarios can run.
- No physical DELETE, broad cleanup, foreign-record mutation, production mapping change, or general cutover is authorized here. Use create/update-only scenarios within manifest scope. Record delete-event behavior as **OMITTED / BLOCKED** unless separately authorized in writing for the exact synthetic record and a reversible recovery path; do not imply that delete permission exists.
- Retain test records, pair/alias rows, queue/audit evidence, and the manifest under the approved retention policy. Do not automatically delete records or clear the test queue. Any later cleanup requires a separate exact-ID disposition plan and approval.

## Deployment approval is not cutover approval

**Approved separately:** deployment of the exact independently reviewed candidate for this controlled test window is a bounded test action, distinct from general cutover. Deployment has **NOT RUN** as of this plan. Before it occurs, record the approval reference, artifact SHA, target service/version, operator, independent stop authority, test window, and confirmed OFF state. This bounded deployment approval does not authorize enabling broad production sync, replaying unrelated queue rows, changing unrelated webhook subscriptions, or starting a general rollout. **General cutover is not approved** and remains a later decision with its own review, evidence, and explicit approval.

## Read-only preflight context (not acceptance evidence)

The [2026-10-20 live preflight](issue-79-live-preflight-2026-10-20.md) reports read-only observations made that day: the service was OFF; active settings version 4 enabled only `PREPARATION` as the deal creation stage; Bitrix24 also exposed `UC_DZSNZ0`, and the corresponding MoySklad status metadata was read, but that stage mapping was not in production settings. The Bitrix24 `event.get` check returned `WRONG_AUTH_TYPE`, so the event registry and callback coverage remain unverified; that response does not prove delivery impossible. The preflight inventory found the nine current-host MoySklad hooks disabled, no current-host invoiceout/service hooks, and no dedicated live-test database/schema. Read-only provider endpoint responses establish only the access/status explicitly described there, not write permissions or genuine callbacks.

Official API facts are limited to their linked source and the dated preflight record. Before a scenario, the operator must confirm current endpoint, permission, pagination, native action semantics, and configured webhook delivery. A documented API method is not proof that this tenant permits it or that a webhook is installed. Where this matrix lacks a verified source for a detail, that detail is a preflight gate—not an assumed capability.

## Entry checklist and completion record

Before the first action, attach: combined-review status and exact SHA; the separate bounded deployment approval (if deployment is required); a fresh test DB/schema migration result; unique run ID and restricted manifest; pinned tenant identities; exact approved settings revision/directions; provider read-only permission check; installed webhook actions and genuine callback test plan; operator and independent stop authority; a precise restoration/retention plan for each synthetic record; and a proved OFF/controlled guard state. A failed or unknown gate leaves that scenario **BLOCKED / NOT RUN**.

For each scenario, record one of `PASS`, `FAIL`, `BLOCKED`, `OMITTED`, or `NOT RUN`, UTC window, artifact SHA, manifest identifier, event/correlation IDs, exact synthetic target IDs in restricted evidence, expected-vs-observed durable state, provider readback, write count, and retained artifacts. Redact credentials, webhook URLs, secrets, customer data, and unrelated IDs. No scenario passes on a mocked provider response, a manually posted webhook, a healthy `/health` response, or a successful API read alone.
