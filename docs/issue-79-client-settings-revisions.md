# Issue #79 client settings revisions

Existing company and contact pairs now advance their field mapping baseline when an event is pinned to a newer settings version. The revision is serialized by the existing pair-scoped client lease and stored in the generic `EntityPairSettingsRevision` table.

The processor compares semantic scalar rules, field groups, and explicit child-resource bindings. Unchanged mappings keep their previous comparison values; removed mappings leave the active projection without writing a clear. A newly added, optional scalar rule with only `Bitrix24 → MySklad` enabled is initialized in that configured direction: the next event reads the current Bitrix24 source field, transforms it using the saved rule, writes only the MySklad target, and verifies the target readback. It never writes the value back to Bitrix24. A newly added rule with `MySklad → Bitrix24` enabled retains the existing MySklad-authoritative initialization behavior. Changes to an existing one-way rule do not inherit the new-rule exception; they remain held for review. Critical rules without a configured reverse direction remain held rather than being guessed.

Revision writes re-read both records before writing and compare the relevant source and target fields with the values used to prepare the write. They re-check the pair lease immediately before each provider write and require exact target readback before advancing the baseline or sync state. A failed write/readback remains retryable with the old baseline and a prepared revision; subsequent work may complete it idempotently. Thus a configured forward write is not marked complete merely because a revision was prepared. The settings save API validates every enabled direction against fresh field metadata, including transform, type, shape, cardinality, and writable constraints. Unsupported/incompatible mappings are rejected server-side even if a client submits a draft directly; the UI's automatic suggestions also exclude incompatible shapes. No implicit type conversion is introduced.

Changed/new child fields continue to use the existing requisite/bank-detail adapter with the explicitly configured parent and child IDs; they are initialized MySklad-to-Bitrix and verified by exact child readback. Unchanged child fields are not rewritten, and removed bindings never clear or delete child records.

Events retain their accepted settings version. An older event is skipped after the pair advances, and a prepared newer revision also fences older events while a retry is pending. A failed readback leaves the revision prepared and the previous baseline intact; a later event can finish the revision idempotently after verifying current external values.

The PostgreSQL APPLY acceptance test exercises the admin settings HTTP endpoint, Bitrix webhook HTTP intake, and loopback Bitrix/MySklad APIs. It covers scalar/reference/group additions, forward-only optional initialization on an existing pair (including failed-readback retry and no reverse write), server rejection of incompatible field type/cardinality, child-only requisite mapping changes, contact pairs with a company parent, removal without clearing, stale pinned events, and retry after an external write whose readback fails.
