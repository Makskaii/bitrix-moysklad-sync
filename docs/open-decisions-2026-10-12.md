## Решения координатора по поручению владельца, 12.10.2026

Владелец разрешил самостоятельно закрыть продуктовые развилки A-01–A-03 и связанные с ними сценарии. Этот раздел имеет приоритет над оставленными ниже исходными вариантами A; технические проверки B остаются открытыми.

### D-01. Счета и связь с заказом

- В обмен входят только счета, созданные после сохранённой границы рабочего запуска. Каждому счёту соответствует отдельная пара B24 smart invoice `entityTypeId=31` ↔ МС `invoiceout`; несколько счетов могут ссылаться на одну сделку/заказ. Не объединять их по номеру, сумме, клиенту или общему заказу.
- Если счёт связан с допустимой новой сделкой, а её заказ ещё не создан, сохранить событие как `WAITING_FOR_ORDER` с причиной. При создании пары сделки и заказа возобновить обработку того же счёта, создать/обновить `invoiceout` и указать его `customerOrder`. Счёт не создаёт заказ в обход стадий.
- Если счёт связан только с исторической сделкой/заказом, отметить `SKIPPED_OUT_OF_SCOPE` с причиной. Более позднее изменение исторического документа не открывает обмен.
- Если новый счёт вообще не связан с допустимой сделкой/заказом либо ссылка неоднозначна, создать случай ручной проверки и не писать счёт во вторую систему. После привязки к допустимому документу повторить обработку того же счёта. Не создавать самостоятельный счёт МС по этому событию.
- Из МС действует тот же принцип: новый `invoiceout` с подтверждённой ссылкой на допустимый `customerorder` связывается с соответствующей сделкой B24; без подтверждённой пары заказа — ожидание или ручная проверка, без угадывания пары.

### D-02. Ранжирование клиентов при недоступной статистике

- Согласованный порядок остаётся `использования → заполненность → самая ранняя дата создания`.
- Если статистика временно не получена либо получена лишь для части кандидатов, не сравнивать неполные значения с полными: повторить чтение, затем оставить событие в ожидании/ручной проверке с причиной. Не создавать нового клиента и не назначать произвольного кандидата.
- Если источник в принципе не предоставляет метрику использований одинаково для всех кандидатов, считать этот критерий равным и перейти к заполненности, затем к дате. Журналировать деградацию и выбранные показатели. Если дата также недоступна или все признаки равны, не склеивать разные записи: отправить на ручную проверку.

### D-03. Предпусковая проверка по включаемой сущности и направлению

- Проверять только реально включаемое направление. Общие блокеры: недоступная БД/миграция, необходимые API-доступы и проверка подлинности событий, отсутствие критичной настройки, которую требует конкретная операция API. Не требовать полного сопоставления всех исторических записей.
- Для сделки/заказа обязательны утверждённые соответствия всех применимых стадий B24 и статусов МС, правила создания на двух согласованных стадиях и зависимые значения (например, служебный контрагент при сделке без клиента). Организация, склад, валюта, ответственный и единицы измерения становятся блокерами только там, где они действительно обязательны для включённой операции; это устанавливается по проверенным API-полям, а не по догадке.
- Для счёта обязательны доступные обработчики событий и рабочий контур пар сделка↔заказ, поскольку счёт должен связываться с заказом. Для товара направление только МС→B24; настроенная группа по умолчанию обязательна, если без неё API не создаёт карточку. Отсутствующие пары отдельных клиентов, товаров, полей или строк не блокируют включение всего сервиса: они обрабатываются по правилам конкретного события и показываются в журнале.
- Необязательные поля/справочники показывать предупреждением. Любую настройку, которая станет блокером после технической проверки, перечислить в интерфейсе вместе с причиной и затронутым направлением.

### D-04. Хранение завершённых решений и аудита

- Рабочие события, попытки API и все категории оперативного журнала (включая ошибки и сообщения об административных действиях) хранить 30 дней; результаты dry — 7 дней. Незавершённые случаи ручной проверки хранить до решения. Отдельный неизменяемый аудит администратора не смешивать с оперативным журналом.
- Решённые случаи ручной проверки и их объяснения хранить 180 дней после закрытия; аудит действий администратора — 365 дней. Эти сроки являются настройками сервера с такими значениями по умолчанию. Каждый файловый журнал ротировать при 200 МБ; ротация не заменяет удаление по сроку. Секреты не сохранять в полезной нагрузке журнала.
- Отсчёт срока для случая ручной проверки начинается с момента его разрешения, а не создания; связанная неизменяемая запись аудита живёт по собственному сроку.

### D-05. Потеря БД без резервной копии

- Сохраняется ранее выбранное отсутствие автоматических резервных копий PostgreSQL. При потере БД сервис немедленно переходит в fail-closed: не принимать новые apply-записи во внешние системы и не считать пустую БД новым рабочим запуском.
- Автоматически не пересоздавать пары, границу запуска и очередь из приблизительного поиска. Перед повторным включением администратор должен восстановить известную прежнюю границу запуска из независимой эксплуатационной записи, заново подтвердить однозначные пары по внешним ID/UUID, вручную разобрать неоднозначные и признать утраченные события. Это отдельная контролируемая процедура, а не обычный restart.
- Без резервной копии события, снимки, аудит и ручные решения, находившиеся только в потерянной БД, **невозможно гарантированно восстановить**. Runbook обязан показать эту потерю и не обещать полного отката. Если позднее потребуется полное восстановление истории, политику резервного копирования придётся пересмотреть отдельно.

## Дополнительные решения координатора, 13.10.2026

Владелец поручил закрыть оставшиеся спорные моменты и сделать feature issues готовыми к работе агента. Решения ниже снимают продуктовые развилки; неизвестные фактические свойства API остаются проверяемыми задачами реализации с указанным безопасным поведением при неподтверждении.

### D-06. Граница ответственности #56 и #60

**Вопрос:** должен ли тикет настроек #56 сам запрещать включение сделок при неподтверждённых стадиях?

**Ответ:** #56 загружает, предлагает, редактирует, подтверждает и сохраняет пары стадий/статусов с явным состоянием `suggested/confirmed/unmapped`; он не включает сделки и не делает runtime preflight. #60 использует сохранённое состояние и блокирует включение только затронутой сущности/направления, пока все применимые пары не подтверждены. #57 предоставляет общий механизм режима. Это не смягчает обязательность проверки, а исключает дублирование реализации в #56 и #60.

### D-07. Недоступные метрики клиента и primary company

**Вопрос:** можно ли ранжировать кандидатов по частично полученным данным и как выбрать компанию контакта без явной основной?

**Ответ:** частичные показатели не сравнивать; после повторной попытки — ожидание/ручная проверка без создания нового клиента. Системно отсутствующая для всех метрика использований считается равной с записью причины; далее сравнить заполненность и дату. При неразрешённой ничьей — ручная проверка. Для контакта использовать только явно заданную основную компанию; если её нет, применять согласованное правило отдельного физического контрагента, не выбирать произвольную из списка. Конкретные источники счётчиков и нормализацию проверить кодом/API; это задача агента, а не новый выбор владельца.

### D-08. Частично переносимый состав заказа

**Вопрос:** блокировать ли весь документ из-за несопоставленной строки или неизвестного денежного преобразования?

**Ответ:** пропустить только строку с недоступным товаром, обязательной ценой/единицей или неподтверждённым преобразованием, сохранить документ и доступные строки, указать ID и причину пропуска в журнале. Если не хватает API-обязательного поля шапки или нельзя достоверно представить общие денежные параметры документа без искажения, не выполнять внешнюю запись документа и отправить случай на ручную проверку. Если внешний API частично выполнил операции до сбоя, зафиксировать фактические ID/состояние и возобновлять адресно; не объявлять серию внешних вызовов атомарной. Цена каталога не меняет существующие строки.

### D-09. Счёт МС без пары заказа

**Вопрос:** выбрать ожидание или ручную проверку для входящего `invoiceout` без подтверждённой пары `customerorder`?

**Ответ:** `WAITING_FOR_ORDER` только если связанный заказ существует, входит в новую область обмена и его пара ещё ожидает завершения; возобновить тот же счёт после появления пары. Если заказа нет, он исторический или связь неоднозначна — соответственно ручная проверка либо `SKIPPED_OUT_OF_SCOPE`; не создавать сделку/заказ/счёт по догадке. Несколько счетов одного заказа всегда отдельные пары.

### D-10. Отсутствие подтверждённого provider request ID

**Вопрос:** можно ли построить идемпотентность на непроверенном `requestId` вебхука МС?

**Ответ:** нет. Если подтверждённый ID доставки/ревизия есть, использовать их; иначе хранить безопасный отпечаток входящего события и ключ сущности, а перед каждой внешней записью читать актуальное состояние, проверять сохранённую пару/версию и результат предыдущей попытки. Дубликат события не должен повторять создание даже при одинаковой payload. Формат вебхука, лимиты и курсоры проверить по документации и тестовым доставкам; неподтверждённое поле не считать обязательным.

### D-11. Удаление и восстановление без гарантированного сигнала API

**Вопрос:** что делать, если код поля `Удалён` не задан либо API не даёт однозначного события восстановления?

**Ответ:** tombstone и остановка пары в нашей БД обязательны; не угадывать код поля и не выполнять запись в неизвестное поле Bitrix24. Отсутствие настроенного кода показывать предупреждением; попытку комментария в timeline выполнять только для подтверждённой живой записи. Автоматическое снятие tombstone допускается лишь при проверенном сигнале восстановления **того же ID**; иначе — ручное подтверждение существования и тождества прежней пары. Ни при каком варианте не удалять вторую запись физически и не создавать новую пару по имени.

### D-12. Два вида административных записей

**Вопрос:** одинаков ли срок технического сообщения категории `ADMIN` и аудита действия администратора?

**Ответ:** нет. Все категории оперативного журнала, включая `ADMIN` и `ERROR`, удаляются по сроку 30 дней (dry — 7). Отдельная неизменяемая аудиторская запись о действии администратора хранится 365 дней. Решённые случаи ручной проверки — 180 дней после разрешения; открытые не удаляются по возрасту.

### D-13. Неизвестная группа/единица/цена товара

**Вопрос:** создавать ли товар с произвольными значениями при отсутствии обязательной пары справочника?

**Ответ:** нет. Для конкретной карточки пропустить неподтверждённое необязательное поле; если создание требует обязательную группу/валюту/единицу, остановить только её создание с объяснением и повтором после настройки. Общая предпусковая проверка блокирует включаемое направление товаров лишь для критичных настроек, реально требуемых подтверждённой API-операцией; название или порядок в списке не доказывают пару. Не создавать товар МС из Bitrix24.

### D-14. Значение статуса `ready-for-agent`

**Вопрос:** означает ли метка готовности, что все реальные API-поля и значения владельца уже известны?

**Ответ:** нет. Тикет готов, когда агент может выполнить указанную проверку кода/API, реализовать положительный путь и безопасное поведение при отрицательном результате без нового продуктового решения. Конкретные ID стадий, складов, организаций, группы товаров, коды служебных полей и секреты остаются конфигурационными входными данными, а не причиной держать тикет в `needs-info`. Готовность к реализации не равна разрешению на production apply, слияние или обход проверки ревью.

- **A — архив исходных развилок:** варианты и рекомендации сохранены для объяснения выбора; все A-01–A-03 закрыты решениями D-01–D-05 выше и больше не требуют ответа владельца.
- **B — техническая проверка:** агент должен проверить код, API, метаданные или фактическую конфигурацию. Вопрос владельцу не нужен, пока исследование не обнаружит реальную развилку.
- **C — исправление документации:** решение уже подтверждено, но требования, спецификация или тикеты ему противоречат либо не отражают его полностью. Это не новый вопрос владельцу.

Неопределённые входные значения, которые администратор задаст в интерфейсе (например, пары стадий, склад или конкретный сотрудник), не считаются открытым продуктовым решением, если формат настройки уже согласован.

## A. Архив закрытых продуктовых развилок

### A-01. Новый счёт без доступного заказа

**Источники:** #1, раздел об области счетов; #55, «Зависимости и TBD».

Новый счёт может быть привязан к исторической сделке, сделке до запуска, сделке вне стадий создания заказа или не иметь ссылки на сделку. Существующий текст запрещает создавать ради него исторический заказ и создавать счёт МС без заказа в сценарии ожидания, но не задаёт общее поведение для остальных случаев.

1. Оставить счёт в ожидании и показать причину; перенести после появления допустимого связанного заказа.
2. Создать/синхронизировать счёт без заказа, если API допускает это; связь добавить позднее.
3. Не синхронизировать такой счёт, явно показать его как пропущенный.

**Рекомендация:** 1 для счёта с будущей сделкой/заказом; 3 для счёта, который не связан с документом, входящим в область обмена. Это соблюдает обязательную связь счёта с заказом и не создаёт заказ ради счёта. Последствие — такие счета не появятся в МС до устранения причины.

### A-02. Что именно блокирует включение сущности или направления

**Источники:** #1, предпусковая проверка; #56, состояния/критичные настройки; #60, preflight.

Стадии и статусы сделок явно должны быть подтверждены до включения обмена сделками. Для остальных сущностей нет полного перечня настроек, отсутствие которых блокирует включение: карты полей, валюты, единицы, склад/организация, служебный контрагент, default group и т. п.

1. Явно задать критичные настройки отдельно по сущности и направлению; только их отсутствие блокирует включение, остальные показывать предупреждениями.
2. Блокировать включение, пока не заполнены все предлагаемые поля и справочники.
3. Блокировать только стадии/статусы, а все остальные пробелы обнаруживать по первым событиям.

**Рекомендация:** 1. Это сохраняет контроль над обязательными зависимостями и не заставляет настраивать неприменимые поля. Последствие — для каждой функции понадобится согласованный список критичных настроек.

### A-03. Срок хранения журналов, не охваченных текущими сроками

**Источники:** #59, ротация и сроки; `requirements.md`, раздел «Админка и наблюдаемость».

Сроки заданы для рабочих событий/API (30 дней), результатов dry (7 дней), открытых случаев проверки и снимков активных пар. Не определён срок хранения завершённых ручных решений, аудита действий администратора и прочих категорий.

1. Хранить аудит и решения ручной проверки бессрочно, остальные завершённые категории — настраиваемый срок.
2. Хранить все категории по единому сроку.
3. Задать отдельный срок для каждой категории.

**Рекомендация:** 3, с разумными значениями по умолчанию и настройкой срока для завершённых журналов. Последствие — администратор сможет разбирать старые решения, но нужно определить размер хранения и правила удаления персональных данных.

## B. Технические проверки, выполняемые без выбора владельца

### B-01. Реальная матрица вебхуков и доставка товарных/заказных событий

**Источники:** #57, intake; #61, карточки товаров; последнее уточнение владельца про события МС.

Проверить read-only фактические подписки МС и обработчики сервиса для создания/изменения товаров и заказов, включая товарные строки; подтвердить подписку на изменения состава заказа и обработку каждого события. Ранее запрос полного списка подписок МС завершался таймаутом, поэтому наличие всех нужных триггеров не подтверждено. Также проверить повторы, секрет и фактическую доставку тестового события. Не считать настроенный endpoint доказательством подписки.

**Ожидаемый выход:** перечень сущность × действие × endpoint × enabled, что реально обрабатывает приложение, пробелы и безопасный способ их закрыть. Если API не сообщает отдельные события товарных строк, установить по документации/фактическому тесту, что изменение строки даёт событие обновления заказа.

### B-02. Создание и обновление частично разрешённого заказа

**Источники:** #54; решения владельца от 12.10.2026.

Проверить по API и локальной реализации, можно ли создать заказ МС с доступными сопоставленными строками, адресно добавлять/менять/удалять строки и повторно прочитать полный состав. Установить, какие обязательные данные нужны для каждой строки и как ошибка одной строки влияет на уже созданный документ.

**Зафиксированное поведение для реализации:** при переходе сделки на разрешённую стадию создаётся заказ с доступными сопоставленными строками; пропущенные строки журналируются. На событиях заказа МС полный состав МС становится источником состава сделки; в Bitrix24 остаются только позиции, для которых подготовлена/сохранена связь с товаром. Изменение каталожной цены не пересчитывает цену строки уже созданного заказа/сделки; цена самой строки документа синхронизируется отдельно.

**Эскалация нужна только если** API не позволяет безопасно сохранить/обновить доступную часть или надёжно отличить ещё не перенесённую строку от удалённой пользователем.

### B-03. Пары товарных строк между системами

**Источники:** #54, состав заказа; архив #16; PR #16 и #26.

Установить доступные идентификаторы строк заказа по обеим сторонам, ограничения на адресное обновление и удаление, поведение при двух строках одного товара, переупорядочивании, частичном чтении и конкурентном изменении. Проверить, можно ли обеспечить уникальную пару строк без сопоставления только по product ID. Если нативной связи нет, подготовить технические варианты хранения пары в БД с их рисками для владельца.

### B-04. Метрики выбора клиентского кандидата

**Источники:** #53; `requirements.md`, правила runtime-поиска.

Проверить, откуда получать использование контрагента/контакта, какие связанные документы считать, как исключать отменённые/удалённые документы и как считать число заполненных полей. Порядок уже утверждён: использование → заполненность → дата создания (самый ранний при равенстве); новый продуктовый выбор не задавать. Предложить детерминированный технический tie-break, если совпадёт и дата.

### B-05. Обязательные поля и служебный контрагент

**Источники:** #53/#54; `requirements.md`, client/order scopes.

Проверить фактические API constraints для создания контрагента, контактного лица и заказа без отдельных полей/строк. Служебный контрагент при полностью отсутствующем клиенте уже согласован как настраиваемая зависимость; конкретное значение задаёт администратор. Проверить, допускает ли API заказ с частично доступными строками и какой минимальный набор полей нужен.

### B-06. Счета: типы, ссылки и связи

**Источники:** #55; `research/invoice-events-research-20261009.md`.

Технически подтвердить поля связи B24 smart invoice (`entityTypeId=31`) с deal, МС `invoiceout` с `customerorder`, cardinality, события и доступные статусы. Исследование webhook уже описало названия событий, но не доказало production roundtrip. Вернуться к A-01 только если фактические ограничения API не позволяют выбранное поведение.

### B-07. Поля, преобразования и справочные значения

**Источники:** #56; отчёты T01/T02/T03/T04; последние материалы #26.

Проверить коды, `title`, тип, направление и writable/create semantics полей по конкретной сущности; множественные телефоны/email, даты/часовые пояса, справочники услуг/организаций/складов/валют, стадии и статусы, скидки/НДС и округление. Известные пользовательские поля и уже одобренные пары не заменять догадками. Неизвестные поля не записывать; API-факт или ограничение возвращать в реестр, а не превращать автоматически в новый бизнес-вопрос.

### B-08. Удаление, восстановление, авторизация и безопасность вебхуков

**Источники:** #57–#59; `requirements.md`, lifecycle/security.

Проверить события удаления/восстановления, возможность однозначно отличить restore от нового объекта, доступность таймлайна и лимиты комментариев; точный B24 `user.admin` check; способ проверки B24/MS webhook credentials, повторов, request ID и ротации секрета. Поля/маркеры и управление доступом уже заданы требованиями; исследование выявляет фактические возможности и не меняет их без отдельной развилки.

### B-09. Отказоустойчивость и потеря БД

**Источники:** #57/#60; `requirements.md`, решение об отсутствии резервных копий.

Технически проверить восстановление очереди и карт, сохранённые cursor/checkpoint, безопасное возобновление после аварии, размеры таблиц и rate limits. Принятое ограничение — не запускать apply с пустой/потерянной БД; подготовить runbook фактического восстановления и остаточные потери. Не менять решение о резервном копировании самостоятельно.

## C. Закрытые расхождения документации (сверка 13.10.2026)

### C-01. Состав заказа при несопоставленной строке

**Решение владельца 12.10.2026:** если сделка на разрешённой стадии содержит строки, которые нельзя передать, создать заказ с доступными сопоставленными строками и записать пропуски в журнал. При изменениях заказа из МС состав МС авторитетен; итоговый состав Bitrix24 приводится к нему, и в Bitrix24 остаются только строки со связанными товарами. Это исключает сохранение исходной несопоставленной строки B24 как будто она по-прежнему входит в заказ.

**Статус:** #1, #54, #61 и `requirements.md` обновлены: заказ создаётся с доступными строками, неизвестный товар МС из B24 не создаётся. B-02/B-03 остаются техническими проверками безопасной адресной записи, а не основанием вернуть старое правило блокировки всего заказа.

### C-02. Цена каталога и цена строки документа

**Подтверждено владельцем 12.10.2026:** изменение каталожной цены МС обновляет карточку товара в B24, но не пересчитывает цену товарной строки уже существующих сделок/заказов. Цена строки — самостоятельное значение документа и обменивается при изменении самой строки.

**Статус:** #54/#61 содержат запрет неявного пересчёта и проверку сохранения цены строки после изменения каталога.

### C-03. Выключение сервиса и период простоя

**Подтверждено владельцем:** после полного `OFF` изменения за период простоя не догоняются. Во время `PAUSE` события поступают и сохраняются, затем обрабатываются после возобновления.

**Статус:** #1, #57 и `requirements.md` приведены к одному правилу: `OFF` не принимает события и не догоняет период простоя; `PAUSE` накапливает очередь.

### C-04. Смена клиента в существующем заказе

**Подтверждено ранее (Q36):** если у уже связанной сделки/заказа изменился клиент, найти/создать нового клиента по runtime-правилам и обновить клиента в том же существующем документе, не создавая новый заказ/сделку.

**Статус:** #54 теперь прямо требует смену клиента в той же паре документов по runtime-правилам #53, журнал и E2E-проверку.

### C-05. Очередность каталога товаров и зависимость заказов

**Решение владельца:** полный feature block #61 публикуется/планируется последним, при этом товарные записи и события МС необходимы, чтобы разрешить новые строки заказа; Bitrix24 должен содержать только позиции с сохранённой парой.

**Статус:** #54/#61 разделяют раннюю минимальную подготовку товара для строк заказа и поздний полный обмен карточками/каталожными ценами. Несопоставленная строка B24 пропускается с причиной, а не блокирует весь заказ.

### C-06. Свежесть опубликованных спецификаций и cross-references

**Источники:** замечания ревью PR #62 и тела #53–#61.

**Статус:** архивной авторской копии тикетов добавлено предупреждение об историческом характере. Нормативны #1 и актуальные #53–#61; в них исправлены references на settings #56, lifecycle #58 и integration #60. Перед слиянием PR #62 остаётся обычное ревью диффа, но не новый продуктовый вопрос.

## Уже решено — не задавать повторно

- `OFF` не догоняет пропущенные изменения; `PAUSE` накапливает события.
- Частичный заказ из доступных позиций создаётся; после событий МС полный состав МС становится авторитетным, Bitrix24 хранит только сопоставленные товарные строки.
- Обновление цены карточки каталога не пересчитывает старые строки документа; цена строки меняется только по событию/изменению самой строки.
- Цена/количество строки — абсолютные значения, не приращения; изменение строки адресное, строки не удаляются и не создаются заново для update.
- Первичная карта клиентов: уникальные UUID→native ID; runtime-поиск компаний/контактов, выбор по usage→filled fields→earliest created date; варианты Q11–Q36 уже согласованы.
- Исторические сделки/заказы/счета до рабочей boundary игнорируются; ни дата паузы, ни рестарт boundary не двигают.
- Карточки товаров только MS→B24; отгрузки и B24 stock accounting вне scope; счета входят в обмен.

## Отдельные входные значения, которые заполняются настройкой

Пары стадий/статусов, реальные пары полей и справочных значений, сотрудники, склады, организация, валюта, default group и служебный контрагент. Их нужно получить/проверить по метаданным и задать администратору в интерфейсе; отсутствие конкретного значения — не приглашение изобретать продуктовую политику.
