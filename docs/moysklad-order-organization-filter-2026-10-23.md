# Заказы МС → сделки Б24: ограничение по организации

Клиент разрешил только два действующих UUID организации МС: `02ada5df-d515-11e2-3c12-7054d21a8d1e` (ООО «АЭРОСИСТЕМЫ») и `a039078a-7cf0-11e7-7a6c-d2a90051dacf` (ОП «Аэросистемы Краснодар»). Они независимо сверены по полному каталогу МС; кавычки в фактических названиях отличаются от текста заявки.

После проверки границы запуска и захвата события, но до поиска пары, создания сделки, переноса строк и обновления полей обработчик CREATE/UPDATE читает исходный заказ МС и его `organization.meta.href`. Только один из двух UUID продолжает обычный обмен. Чужая организация завершает событие статусом `SKIPPED_DISABLED` / `ORDER_ORGANIZATION_EXCLUDED`; отсутствующая, повреждённая или противоречивая ссылка — `MANUAL_REVIEW` / `ORDER_ORGANIZATION_UNVERIFIED`. Ошибка чтения провайдера остаётся повторяемой, явный отказ чтения уходит на разбор. Такую проверку проходят и новые, и уже связанные заказы; направление Б24 → МС не меняется.

Для DELETE заказа МС карточка источника уже может отсутствовать. События DELETE оставлены на существующем жизненном цикле пар: фильтр на чтение организации к ним не применяется. Удаление не создаёт новую сделку; политику удаления существующих связей следует отдельно согласовать, если заказ сменил организацию до удаления. Существующие ранее перенесённые сделки других организаций не удаляются и не переписываются задним числом.

Проверка до передачи на слияние: API `tsc`/build PASS, компиляция test TS PASS, два focused unit tests PASS. Живую обработку разрешённого и запрещённого заказа на этой локальной ветке ещё не проводили; текущий прод не изменён. При слиянии нужен обычный выпуск runtime и ограниченная проверка трёх новых событий (каждая разрешённая организация и одна запрещённая) с нативным readback в Б24 и БД, без повторной отправки сомнительных старых событий.
