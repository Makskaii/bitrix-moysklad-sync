# Issue #79: field metadata and explicit transforms

Field settings use provider metadata rather than record values to populate the mapping catalog. Candidate metadata retains the provider title (or an honestly blank title), API field code, type, shape, cardinality, enum option IDs/values, reference kind when known, and writability evidence. Bitrix24 enumeration options missing from the list response are retrieved through the corresponding official `*.userfield.get` method. Catalog `propertyNNN` title/type/cardinality and list options are enriched using `catalog.productProperty.list` and `catalog.productPropertyEnum.list`; only a matching product-field schema entry is shown (metadata alone never invents a writable field). Invoice user-field titles/options are retained from `crm.item.fields`. A metadata field is not treated as writable unless the provider schema explicitly says so.

The pure conversion contract is `apps/api/src/field-settings/field-transform.ts`. `applyFieldTransform` returns `mapped`, `skip`, or `error`; null/missing is not conflated with empty string, zero, or false. Conversions must be explicit: strict number parsing and precision/range policy, IANA timezone for date conversions, explicit boolean values, exact option/reference pairs, and explicit cardinality strategy. `semanticFieldRule` and `semanticFieldGroup` provide the shared semantic projection for settings comparison; display labels and UI order are excluded.

Enabled rules are checked against live metadata before activation. Copy needs exact type/shape/cardinality compatibility. Inactive/TBD rules remain drafts; active incompatible rules are rejected by the admin API. Preview invokes the same pure conversion contract. Invalid optional values return a field-level reason; callers must stop on invalid critical fields. The editor exposes targeted number/date/boolean controls, exact-ID enum dropdown pairs with human labels plus IDs, and JSON for advanced transforms. Standard field titles are shown before API codes; cardinality and writable evidence remain visible.

Catalog product custom properties remain visible when metadata describes them, but active MySklad-to-Bitrix24 property writes are rejected (UI marks the field unavailable) until the Bitrix24 property request payload adapter is verified. Metadata presence alone does not prove payload compatibility or writability. Bitrix24 catalog-originated product writes remain prohibited. Deal/order rebase hooks also fail closed for changed groups, dictionary rules, missing values, and changed mappings without enabled MySklad-to-Bitrix24 authority; verified scalar rules are read back before returning a baseline projection. Runtime transforms are consumed by contacts, clients, invoices, and deal/order fields; catalog rules are integrated by the catalog owner for supported scalar properties only.
