# Event intake and queue behavior

This service acknowledges a webhook only after its event has been durably stored in PostgreSQL. Processing runs asynchronously from the persisted event; provider workers are started after the HTTP response finishes, so the acknowledgement does not wait for synchronization to complete. Configure both endpoints over HTTPS and store credentials in the deployment's secret store; never include live credentials in this document, URL examples, logs, or support output.

## Endpoints

| Provider | Method and path | Authentication |
| --- | --- | --- |
| Bitrix24 | `POST /webhooks/bitrix24` | `auth.application_token` must match `BITRIX24_EVENT_APPLICATION_TOKEN`. |
| MoySklad | `POST /webhooks/moysklad/{secret}` | The path segment must match `MOYSKLAD_WEBHOOK_SECRET`. |

Set `SYNC_MODE` to `apply` or `dry` on the server at process start; the admin UI cannot change it. In `apply`, `DATABASE_URL` selects the working database. In `dry`, `DRY_DATABASE_URL` is required, and the process refuses startup unless it resolves to a different PostgreSQL database or schema from `DATABASE_URL`. The apply process also refuses a `DATABASE_URL` that resolves to the configured dry target. URL spelling, host case, default port, and credentials do not bypass this comparison. Both schemas receive the same migrations. The service rejects intake when the configured service mode is `off`. In `pause`, verified events are stored and wait for processing to resume.

Bitrix24 sends a single event envelope. The application token is removed from the stored payload. MoySklad may send an `events` array; each item is stored as its own queue event, and the service does not acknowledge the batch unless all items have been persisted. MoySklad's [webhook guide](https://github.com/moysklad/workbook-api-doc/blob/master/pages/workbook/articles/webhooks.md) documents a `requestId` query parameter and states that it remains the same on delivery retries. When supplied, the queue key combines that ID, the event's batch position, and a payload fingerprint. Neither provider's event format is assumed to have a stable delivery ID when one is absent, so each such arrival receives a unique key and is retained (at-least-once intake); this avoids incorrectly collapsing two later genuine updates that happen to have identical webhook envelopes. Downstream processing must reread current entity state and tolerate repeat processing.

Direction-disabled events are stored as terminal skips with `DIRECTION_DISABLED`. `off` returns HTTP 410 without storing the event. Authentication failures do not write events. Logs contain safe event metadata only, never the credentials or complete provider payload.

## Provider setup and verification

Register only event types whose entity direction is enabled and whose processor is implemented and enabled in the service. Configure the Bitrix24 application token and MoySklad secret independently. Do not copy the MoySklad secret into a query parameter; it belongs only in the configured path segment.

The repository does not assert which event subscriptions are currently installed in a live Bitrix24 portal or MoySklad account. Verify the account's actual subscription list and perform a controlled test delivery before enabling a direction. MoySklad documents `requestId` retry behavior, but the service still supports events without that query value through at-least-once intake. This implementation does not call either provider to configure subscriptions.

## Processing safety

Workers read current provider state and persist event, API-attempt, retry, review, pair, settings, checkpoint, and log state in the database selected at process start. The existing client and product processors can reconcile in dry mode; an enabled local deal/order header processor can also run its existing limited field mapping. Each proposed external mutation is stored in `DryRunWriteProposal`, and subsequent reads in that dry run see a virtual readback of the proposed fields. Provider adapters record those proposals without sending mutating HTTP requests. A dry proposal cannot be replayed in apply because apply starts against a separately validated database/schema. A worker restart rediscovers only the pending events in its selected database.

Dry startup fails closed when either database URL is missing or both URLs resolve to the same database and schema. Configure a disposable, UTF-8 PostgreSQL schema for dry mode and apply migrations to it before starting the service. Never point the dry URL at the working schema. Transient provider read failures remain retryable; events requiring a human decision are held for manual review.

Event workers share four PostgreSQL-backed renewable slots. Each slot has an owner token; workers revalidate ownership before side-effect and completion boundaries, and client processors retain source/pair locks through those boundaries. Contact processing also locks its unresolved primary company before lookup or create, then keeps that company's pair lock after resolution. A remote API and PostgreSQL cannot participate in one atomic transaction: if a provider accepts a create just as a worker loses its lease or its response is interrupted, the request may already have taken effect. Before a client create, the event is marked `CLIENT_CREATE_IN_PROGRESS` durably; a stale marker is promoted to manual review and is never automatically re-created. A confirmed create clears the marker in the same transaction that persists its pair. Other processing retries reread current provider state and verify writes before advancing synchronization state. This residual uncertain-response window is not claimed to be exactly-once delivery.

The stored database is the source of truth for queue recovery. If it is lost, do not start `apply` against a new empty database: the former launch boundary, queue, event history, and audit cannot be reconstructed from the replacement database. Follow the controlled recovery procedure and confirm the prior boundary and pairs before re-enabling writes.

## Scope and remaining #57 work

This branch implements a reviewed safety slice, not the complete #57 feature. Client company/contact, email-contact, product-card, and the enabled local deal/order header paths schedule transient provider failures durably, parse bounded `Retry-After` seconds or HTTP dates, and hold permanent provider 4xx failures for review. Provider timeouts remain uncertain until current-state readback; client creates retain a durable in-progress marker and can only be cleared after the created pair is persisted. Database failures and lease loss do not advance event state; stale processing claims are recovered after the lease window. Client company/contact events also have atomic durable claims, source/pair leases, a persisted `On` write gate, dry/apply database isolation, and virtual write proposals. The four worker slots are a capacity limit; event and pair ownership is enforced separately for the client processor.

Webhook acceptance tests exercise the actual Bitrix24 and MoySklad HTTP routes. They verify independent provider credentials, durable acknowledgement before response, at-least-once Bitrix24 delivery, MoySklad per-item batch persistence and `requestId` retry deduplication, and that acknowledgement completes while a worker remains blocked. They also cover invalid credentials, malformed batches, Off/Pause intake, disabled directions, and persistence failures.

The fake-provider acceptance test also drives a MoySklad product update through the real webhook controller and event processor for an existing active product pair. It verifies current reads from both providers, the fixture-pinned product field configuration, reconciliation, apply write/readback, and dry virtual readback from a stored write proposal without external writes. This route-level slice uses an in-memory persistence fixture; PostgreSQL-backed queue, pair-lock, and state behavior remains covered separately. It does not make product cards fully enabled in the deployment readiness gate or cover product create/delete events.

Nightly reconciliation runs at 01:00 Europe/Moscow for the preceding 24 hours, only while global mode is On and no OFF/PAUSE interval overlaps that window. It runs against whichever server-selected database is active; in dry mode, resulting queue rows stay in the isolated dry schema. It queries Bitrix24 contact and company `updatedTime` feeds using the documented stable-ID keyset (`>id`, `start=-1`) and MoySklad counterparty `updated` records with one-second minimum spacing between provider requests. MoySklad counterparty pagination beyond one 1,000-row page fails closed because stable UUID keyset filtering is not verified in the official contract; it queues no partial page and does not checkpoint that cursor.

For active MoySklad company pairs, the nightly worker also reads each nested contact-person collection using the documented `limit`/`offset` endpoint ([MoySklad JSON API](https://dev.moysklad.ru/doc/api/remap/1.2/)). It validates the advertised total and each page before staging events, caps a single company collection at 20 pages, and queues only records whose `updated` timestamp falls inside the same 24-hour window. It stages the contact-person events until all selected collections finish, then stores durable `contactperson` updates with the parent URL so the existing client processor can resolve the company dependency. If a collection is over the bound, changes size mid-scan, or returns inconsistent metadata, the provider feed stays retryable and none of its staged contact-person events are queued. This is a bounded scan of active paired companies, not a global MoySklad contact-person change feed; provider pagination uses offset and can require a full scoped retry after concurrent collection edits.

A PostgreSQL-backed expiring run lease with an ownership token fences concurrent replicas; provider pages are interpreted using the exact entity, parent, and offset queried, and the counterparty cursor advances only after page IDs have been durably queued. If ownership is lost during a provider call, already queued events are replay safe through idempotent event keys. Each provider retains its own retry status so one unavailable API does not prevent the other feed from queuing work. Events use the current pinned field-settings version.

This nightly slice does not scan historical deal/order archives or catch up after downtime. It does not cover delete or archival changes; the status reports these limits. Database-loss recovery now persists an administrator-confirmed launch boundary and audit record, as described in [database-loss recovery](../database-loss-recovery.md). Invoice routing, full deal/order dependency resolution, and end-to-end timeout/lost-response coverage across every provider/entity combination remain incomplete. Keep those paths disabled and treat this branch as partial until each gap has its own verified implementation and independent acceptance review.
