# Local-only deal header exchange checkpoint

This is a temporary development checkpoint, not an approved production mapping or a completed dry-run/apply workflow. It supports only already-persisted, active `DEAL` pairs and a pinned `deals-orders` copy rule for Bitrix24 `COMMENTS` ↔ MoySklad customer-order `description`. It never creates documents or writes positions, product rows, totals, IDs, metadata, or other fields. The initial bilateral baseline is captured without writes; later updates require a successful target readback before the last-success state advances. MySklad wins when both sides changed since that state, and equal values are treated as echo/no-op.

The writer is server-side and remains disabled unless all of these are true: `ADMIN_PREVIEW=1`, `LOCAL_HEADER_EXCHANGE=1`, `LOCAL_HEADER_EXCHANGE_READY=1`, `SYNC_MODE=apply`, the persisted service mode is `on`, and both upstream base URLs are literal loopback HTTP endpoints (`127.0.0.1` or `::1`). The separate readiness flag is required because the general sync-mode entity control still marks deal/order exchange not ready. Do not enable these flags in a deployed environment or configure real CRM/MoySklad endpoints. The field mapping is still TBD/unapproved; the COMMENTS↔description test fixture is not authorization to enable it for real accounts.

Verification uses the isolated `issue14_apply_test` PostgreSQL schema and fake HTTP servers bound to `127.0.0.1`; it asserts both directions, conflict behavior, readback, no-op echoes, unmatched-pair hold, disabled gate, and rejection of non-loopback endpoints. This checkpoint does not complete issue #14 (durable dry-run plans/results and production-vs-dry isolation remain separate work), nor does it implement order creation or line-item synchronization.
