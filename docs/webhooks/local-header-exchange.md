# Local-only deal header exchange checkpoint

This temporary checkpoint describes only the `COMMENTS` ↔ `description` header writer; it is not an approved production mapping or a completed dry-run/apply workflow. It supports only already-persisted, active `DEAL` pairs and a pinned `deals-orders` copy rule. It never creates documents or writes positions, product rows, totals, IDs, metadata, or other fields. The writer requires the local preview gates below; those gates do not control first-event baseline capture.

For an accepted first event on an already-confirmed historical deal/order pair, Q26.66 requires reading both current documents and persisting their settings-versioned baseline before field processing. This event-driven baseline capture is independent of `ADMIN_PREVIEW`, `LOCAL_HEADER_EXCHANGE`, and `LOCAL_HEADER_EXCHANGE_READY`; it is not a sync write. `SYNC_STATE=off` rejects intake before persistence or pair/baseline work. `pause` accepts and persists the event and may perform the two read-only baseline source reads, but performs no external sync writes. In `SYNC_MODE=dry`, the baseline is stored only in the isolated `DRY_DATABASE_URL`; baseline reads may contact the configured source APIs, but no external writes are made. If the pair, source reads, settings version, or baseline persistence is not safe, hold the event for manual review rather than guessing or replacing an existing baseline.

Once a baseline is ready, the distinct local header writer remains disabled unless all of these are true: `ADMIN_PREVIEW=1`, `LOCAL_HEADER_EXCHANGE=1`, `LOCAL_HEADER_EXCHANGE_READY=1`, `SYNC_MODE=apply`, the persisted service mode is `on`, and both upstream base URLs are literal loopback HTTP endpoints (`127.0.0.1` or `::1`). The separate readiness flag is required because the general sync-mode entity control still marks deal/order exchange not ready. Do not enable these flags in a deployed environment or configure real CRM/MoySklad endpoints. The field mapping is still TBD/unapproved; the COMMENTS↔description test fixture is not authorization to enable it for real accounts.

Verification uses the isolated `issue14_apply_test` PostgreSQL schema and fake HTTP servers bound to `127.0.0.1`; it asserts both directions, conflict behavior, readback, no-op echoes, unmatched-pair hold, disabled gate, and rejection of non-loopback endpoints. This checkpoint does not complete issue #14 (durable dry-run plans/results and production-vs-dry isolation remain separate work), nor does it implement order creation or line-item synchronization.
