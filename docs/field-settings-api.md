# Настройки полей: API и версия

Все маршруты доступны только администратору Bitrix24. Каталоги и предпросмотр выполняют только чтение внешних систем; они не пишут в Bitrix24/МойСклад, не регистрируют вебхуки и не создают фоновые задания.

## Настройки и версии

- `GET /api/admin/field-settings` возвращает `{ version, createdAt, config, references }` активной версии.
- `GET /api/admin/field-settings/versions/:version` возвращает неизменяемую сохранённую версию.
- `PUT /api/admin/field-settings` принимает `{ config }`, проверяет состав полей по текущим каталогам, записывает новый снимок и атомарно переключает active pointer. Ответ — новый `{ version, createdAt, config, references }`.
- Сущности правил ограничены `contacts`, `contacts-companies`, `companies`, `deals-orders`, `catalog`. Схемы полей загружаются на уровне сущности и не требуют активной пары; при сохранении также не требуется выбрать пару. Preview сверяет каждое поле с live metadata каждой запрошенной активной пары и откажет, если хотя бы в одной паре поле отсутствует. Любое поле Bitrix24 принимается как write-target только при явном `isReadOnly: false` в live metadata; неизвестная writable-семантика безопасно блокируется. `id`, `meta`, `positions`, `payedSum` и системные поля также запрещены как write-target. Исполнитель обязан повторно безопасно удержать событие, если поле отсутствует в конкретной паре события.
- `config.rules[]` содержит entity, sourceField/targetField и независимые `bitrix24ToMoysklad` / `moyskladToBitrix24` с `enabled` и `transform.kind` (`copy` или `tbd`). `config.groups[]` задаёт направленный `join-non-empty` с конфигурируемым разделителем. TBD сохраняется как неразрешённое преобразование и возвращает ошибку preview; обработчик не должен его применять.
- `config.references.units[]` и `priceTypes[]` сохраняют все текущие исходные записи, целевой UUID или `null`, подписи и состояние. Текущая доступность целевых UUID перепроверяется по live read-only каталогу перед активацией. Повторное назначение одной целевой единицы/типа цены двум исходным запрещено.
- `config.references.dictionaries[]` хранит идентификаторы типизированного поля/справочника и явные пары значений. Утверждённые стартовые пары — данные, а не доказательство готовности записи во внешнюю систему.

Кнопка «Сопоставить автоматически» в редакторе создаёт только видимые несохранённые предложения. Она сравнивает отображаемые названия после удаления крайних пробелов, схлопывания повторных пробелов и приведения регистра; совпадение должно быть уникальным с обеих сторон и иметь совместимые типы. Заголовки пользовательских полей Bitrix24 уточняются через entity-specific `crm.*.userfield.list` с `filter[LANG]=ru`, сопоставленные только по точному `FIELD_NAME`. Провайдер следует целочисленному `next` в последующем `start` до отсутствия следующей страницы, в пределах 20 страниц; некорректная строка, повторный/нерастущий курсор и недостающее продолжение при несовпадении `total` дают ошибку каталога вместо неполного ответа. Поле формы имеет приоритет над заголовком списка и фильтра. Общие заголовки вроде «Пользовательское поле (Строка)», пустые заголовки и заголовки, совпадающие с кодом, не участвуют в автоматических предложениях. Стандартные поля и пользовательские поля показываются отдельно. Коды полей сохраняются как значения правил; названия не используются во время обмена. Неоднозначные, несовместимые, уже занятые правилами или недоступные по направлению поля остаются несопоставленными. Для новых предложений оба направления остаются отключёнными, преобразование — `tbd`; администратор должен явно выбрать допустимое направление и настроенный трансформ. Сохранение выполняется только существующей кнопкой сохранения версии.

История версий append-only. Приём нового события сохраняет событие и его версию одним DB-транзакционным действием. Изменение active pointer влияет только на новые события. Retry/resume читает только `InboundEventSettings.settingsVersion`; он не запрашивает активную версию. Только подтверждённый individual recompute может перепривязать одно доступное событие к текущей версии. Bulk-replay API отсутствует.

## Каталоги

`GET /api/admin/field-settings/catalogs` получает актуальные единицы и типы цен из `catalog.measure.list`, `catalog.priceType.list`, `GET entity/uom` и `GET context/companysettings/pricetype`. Интеграционные провайдеры внедряются через `ReadOnlyFieldDataProvider`; тесты подменяют их HTTP boundary. Чтение Bitrix24 использует короткоживущий admin bearer текущего запроса, МойСклад — server-side `MOYSKLAD_API_TOKEN`; ни один токен не возвращается клиенту или в диагностику.

Внешние коллекции листаются явно. Ответ включает полную коллекцию, если она укладывается в установленные 20 страниц по 50 записей; при превышении лимита или ошибке источник возвращает 503, а не тихо обрезанный список. Для более крупных справочников интерфейс должен перейти на явный cursor/page запрос.

## Безопасный предпросмотр

Техническое соответствие сущностей: `contacts → CONTACT`, `companies → COMPANY`, `deals-orders → DEAL`, `catalog → PRODUCT`; смарт-счета отложены и не дают активных пар для этой страницы. Схемы полей доступны без пар.

`POST /api/admin/field-settings/preview` принимает `{ entity, direction, pairIds: [entityPairId], config? }`. На один запрос разрешено 1–10 уникальных ID; сервер заново проверяет, что каждая пара существует, активна и относится к выбранной сущности, поэтому клиент не может подставить произвольные внешние ID. Для каждой активной пары сервер читает обе записи, применяет draft config (либо текущую активную) только для совпадающей сущности и возвращает `pairId`, читаемую подпись, исходные значения, вычисленный результат, текущее значение target, ошибки, версию и `writes: 0`.

`GET /api/admin/field-settings/fields?entity=...` возвращает схему указанной сущности без выбора пары: коды, названия, типы, writable-семантику и категорию поля (`standard` или `custom`), не значения записей. Категория пользовательского поля определяется провайдером по типу источника: Bitrix24 `UF_CRM*` (и `property*` для каталога) и атрибуты МойСклад; неизвестные коды не считаются пользовательскими автоматически. Для контактов, компаний и сделок провайдер соединяет CRM schema с `crm.contact.userfield.list`, `crm.company.userfield.list` или `crm.deal.userfield.list` соответственно по точному `FIELD_NAME`; каталогские поля остаются на `catalog.product.getFieldsByFilter`. Для каталога МойСклад имена атрибутов берутся из `/metadata/attributes`, а стандартные поля описываются справочником кодов данного ресурса. Методы, наблюдения и остаточные ограничения записаны в [исследовании меток полей #10](../research/issue-10-field-labels.md). Preview по-прежнему требует активные пары; неуспешное чтение пары не представляется успешным предпросмотром. Ни запись полей, ни массовые выборки, ни PII в operational logs не выполняются.

## Внешние read-only методы

- Bitrix24: `catalog.measure.list`, `catalog.priceType.list`, `crm.contact.fields` + `crm.contact.userfield.list`, `crm.company.fields` + `crm.company.userfield.list`, `crm.deal.fields` + `crm.deal.userfield.list`, `catalog.catalog.list`, `catalog.product.getFieldsByFilter`; для предпросмотра пар — `crm.contact.get`, `crm.company.get`, `crm.deal.get`, `crm.item.get` (entity type 31), `catalog.product.get`.
- МойСклад JSON API: `GET entity/uom`, `GET context/companysettings/pricetype`, и GET ресурсов пары для `counterparty`, `customerorder`, `invoiceout`, `product`.

Контракт не подтверждает product-row ID pairing, pack factor, права записи, production activation или разрешение выполнять исходящие вебхуки.
