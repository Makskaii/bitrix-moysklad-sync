Карта направленная:18 значений Б24→МС,18 native значений МС→Б24.
Первые15пар действуют в обе стороны. По прямому решению пользователя:

- UC_BBJSFZ«Отменен покупателем»→МС703b0c0d...«отменен».
- LOSE«Не успешно»→тот же МС703b0c0d...«отменен», только вперёд.
- МС703b0c0d...«отменен» и296124dc...«Отменен»→UC_BBJSFZ,
  НИКОГДА не LOSE. Обратная запись не меняет выбранный исходный статус МС.
- UC_RH2DBY«Возврат средств»↔МС47deae3c...«возврат».
- Повтор/echo после LOSE→«отменен» не переклассифицирует исходную LOSE;
  новая независимая смена статуса МС на одну из отмен выбирает UC_BBJSFZ.

Для существующих документов используется отдельный
`dealOrderRuntime.stageTransitions` с массивами `bitrix24ToMoysklad` и
`moyskladToBitrix24`. В каждом массиве источник уникален; несколько источников
могут иметь одну цель. В отсутствие нового свойства старая двусторонняя карта
`stages` сохраняет прежнее поведение.

Создание заказа из новой сделки остаётся разрешённым только на
PREPARATION/«Обработан»: creation `stages` не расширяем и не заменяем.
Default создания сделки из несопоставленного статуса МС также не меняется.

## Прочие статусы

Прочие специфичные статусы МС не имеют пары в основной воронке и остаются
  несопоставленными; не создавать стадии/финансовые документы автоматически.

## Найденные и исправленные препятствия runtime

1. При отсутствии обычных rules сделки обработчик выходил до обработки стадий,
   сообщая SYNCED без изменения целевого статуса. Теперь configured stages
   обрабатываются независимо от scalar rules.
2. Проверка RFC variant отвергала native MS state IDs с четвёртой группой0a80.
   Stage-only validation принимает точную UUID-shape; общий валидатор других
   полей не ослаблен. Origin/path/type/status mapping uniqueness сохраняются.
3. Новый baseline не сохранял native:stage. Теперь обе стадии проектируются
   из проверенной карты. Для legacy snapshot bootstrap разрешён без provider
   writes только когда оба реальных статуса уже соответствуют одной паре;
   разногласие остаётся MANUAL_REVIEW, приоритет задним числом не угадывается.
4. Stage PUT использует обязательные MS charset/gzip headers.

## Процедура внедрения (выполнена 21.10.2026)

Только координатор имеет право менять общие production settings и artifact.
После слияния исправлений, при штатной паузе и текущей версии настроек,
добавить только `dealOrderRuntime.stageTransitions`:

```js
const pair = ({bitrix24StageId,moyskladId}) => ({bitrix24StageId,moyskladId});
stageTransitions = {
  bitrix24ToMoysklad: map.pairs.map(pair),
  moyskladToBitrix24: [...map.pairs.filter(p => p.moyskladToBitrix24 !== false),
                     ...map.reverseAliases].map(pair)
};
```

Сохранить все остальные поля конфигурации, включая creation `stages` и
`references.namedPairs`. Дублировать canonical namedPairs ради направленных
alias НЕ нужно. Использовать обычный
FieldSettingsService.save и проверку свежих каталогов, не SQL UPDATE.
Сервер проверяет каждый runtime STAGE_ID через canonical catalog key и каждый
MS state ID по актуальным каталогам; конфликтующие источники внутри одного
направления отвергаются HTTP400, настройки не активируются.
Только PREPARATION creationEnabled.
Проверить точную разницу версии/прежние9UOM/7price и все прочие правила.

Перед первым live-переходом на ранее созданной тестовой паре138230/13f339d5...
отправить обычное genuine provider UPDATE при обеих стадиях «Обработан»,
дождаться успешной обработки и появления native:stage в snapshot (без seed).
Затем по одному переходу: Б24«Резерв»→МС«Резерв», Б24«Комплектация»→МС,
МС«Подтвержден»→Б24, МС«Обработан»→Б24. Проверять событие/readbacks/одну
пару/прежний состав/274руб; финальные/отменные стадии не нужны для smoke.
Не сбрасывать и не переигрывать старые held события.

На подготовке: реальные каталоги прочитаны; локальные PostgreSQL+synthetic HTTP
проверяют actual field runtime, baseline и mode/direction gates. Это НЕ
production acceptance. Настройки/стадии провайдеров на этом шаге не менялись.
