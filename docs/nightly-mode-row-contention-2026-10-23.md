# Nightly lease contention

Production observation on 23 October found a nightly `SELECT ... FOR UPDATE` waiting more than 90 seconds behind overlapping provider transactions on the global SyncSetting row. A rotating sequence of short blockers can keep a statement waiting longer than each individual lock timeout. `NOW()` also uses the transaction start time: an update delayed by a conflicting row lock can report success with an expiry already in the past.

Provider operations now hold `FOR KEY SHARE` on the authoritative mode row. Every runtime writer of serviceMode (the normal setter, startup recovery fail-closed path, fresh-start confirmation and recovery confirmation) takes `FOR UPDATE`, so an acknowledged OFF still waits for already started provider work and the next provider operation reads OFF. Nightly metadata claim/renew uses `FOR NO KEY UPDATE`, compatible with the provider gate. Its transaction has an absolute statement timeout as well as a lock timeout; lease clocks are evaluated with `clock_timestamp()` only after obtaining the row lock. An expired lease is rejected rather than revived. Other admission/pinning fences remain in place.

The real PostgreSQL regression uses an isolated synthetic database. It demonstrates the old stale-clock behavior with a scaled lease and held SHARE lock, rejection of expired ownership, renewal of live ownership, renewal while a provider gate is held, and the actual mode setter waiting for that gate before OFF acknowledgement. The existing real PostgreSQL header-mode test also verifies that OFF prevents the next provider request. Relevant unit/build checks pass. Live nightly completion remains a separate acceptance criterion; successful deployment alone does not establish it.
