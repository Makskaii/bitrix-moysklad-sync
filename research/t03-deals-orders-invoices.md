# T03 — сделки, заказы покупателей и счета

Проверено 2026-09-28. Область: [T03](https://github.com/Makskaii/bitrix-moysklad-sync/issues/4) в рамках [спецификации #1](https://github.com/Makskaii/bitrix-moysklad-sync/issues/1). Ниже отдельно приведены документационная модель API, полученные live-метаданные Bitrix24 и непроверенные данные/связи. Доступ к live API не означает, что фактический поток HTMLStudio или все поля конкретных записей установлены.

## Подтверждённая API-модель

| Область | Документированные коды и связи | Что ещё нельзя считать соответствием полей |
| --- | --- | --- |
| Сделка Bitrix24 | Тип CRM `entityTypeId=2`; современный `crm.item.*` использует `stageId`, `categoryId`, `companyId`, `contactIds`, `assignedById`; прежний `crm.deal.*` — `STAGE_ID`, `CATEGORY_ID`, `COMPANY_ID`, `CONTACT_IDS`, `ASSIGNED_BY_ID`. Позиции доступны через `crm.item.productrow.*` с `ownerType=D`. У сделки одна компания и несколько контактов; `crm.deal.get/list` не возвращают полный `CONTACT_IDS`, для него нужны `crm.deal.contact.items.*` или универсальные методы. [Bitrix24: сделки](https://apidocs.bitrix24.com/api-reference/crm/deals/), [контакты сделки](https://apidocs.bitrix24.com/api-reference/crm/deals/contacts/index.html), [поля сделки](https://apidocs.bitrix24.com/api-reference/crm/deals/crm-deal-fields.html). | Наличие поля в API не доказывает, что HTMLStudio переносит его или что оно заполнено на портале. Значения воронок и стадий зависят от аккаунта; для них нужны `crm.status.list`/метаданные портала. [Bitrix24: поля CRM](https://apidocs.bitrix24.com/api-reference/crm/main-entities-fields.html). |
| Заказ покупателя МойСклад | Тип и endpoint `customerorder`; документ имеет ссылочные поля, включая `agent` (контрагент), `owner` (сотрудник), `state` (статус), и `positions` (позиции). У документов позиции можно читать/менять отдельным ресурсом; передача полного массива `positions` при обновлении заменяет весь состав. Статусы доступны через метаданные типа, а значения и ID задаются аккаунтом. [МойСклад: JSON API 1.2](https://dev.moysklad.ru/doc/api/remap/1.2/). | `agent` не даёт автоматически однозначного соответствия компании и контакта Bitrix24; фактическую схему контрагентов и контактных лиц надо проверить на связанных документах. `owner` нельзя без проверки приравнять к ответственному Bitrix24. |
| Счёт покупателю МойСклад | Тип и endpoint `invoiceout`; документ поддерживает позиции и статусы, как документ МойСклад. [МойСклад: JSON API 1.2](https://dev.moysklad.ru/doc/api/remap/1.2/). | Связь конкретного `invoiceout` с заказом и сделкой, номера, статусы и заполненность полей не установлены без выборки аккаунта. |
| Счёт Bitrix24 | Есть старый тип `entityTypeId=5` и новый смарт-счёт `entityTypeId=31` (`SMART_INVOICE`). `crm.item.*` работает с новым типом; для старого возвращает `ENTITY_TYPE_NOT_SUPPORTED`. У нового счёта документированы `accountNumber`, `stageId`, `companyId`, `contactIds`, `assignedById` и связь со сделкой через `parentId2`; позиции — `crm.item.productrow.*` с `ownerType=SI`. [Bitrix24: типы CRM](https://apidocs.bitrix24.com/api-reference/crm/data-types.html), [счета](https://apidocs.bitrix24.com/api-reference/crm/universal/invoice.html), [поля объектов](https://apidocs.bitrix24.com/api-reference/crm/universal/object-fields.html). | Документационная модель не подтверждает, что каждая историческая запись имеет `parentId2` или тот же набор заполненных связей. |

`crm.deal.fields` вернул 143 поля. `crm.item.fields(entityTypeId=31)` вернул схему нового типа; `crm.invoice.fields` старого типа содержал 44 поля по подсчёту ответа. В отфильтрованном выводе старой схемы подтверждён только код `ID` → «ID» → `integer`; остальные поля здесь не перечисляются, поэтому эта таблица не является полной картой legacy-счёта. Поиск соответствия пользовательских полей Bitrix24 ID МойСклад по названиям в текущем выводе не дал проверенного кода; не считать его отсутствующим.

Первая страница `crm.item.list(entityTypeId=31)` вернула 1 запись, а первая страница `crm.invoice.list` — 0. Это подтверждает наличие нового счёта и отсутствие старых счетов только в запрошенной выборке; страницы не обходились, поэтому это не доказывает, что старых счетов в портале вообще нет.

`crm.status.list` по `DEAL_STAGE` вернул 18 пар кода и названия: `NEW` — «Новый»; `PREPARATION` — «Обработан»; `UC_7QBU06` — «Резерв»; `PREPAYMENT_INVOICE` — «Комплектация»; `EXECUTING` — «Подтвержден»; `UC_66WY4D` — «Согласован»; `UC_DZSNZ0` — «Передан на сборку»; `UC_G3M2W5` — «На сборке»; `UC_LYM82H` — «Собран без расхождений»; `UC_TW61UY` — «Собран с расхождениями»; `UC_LNVWT2` — «Частично укомплектован»; `UC_TA3DQ2` — «Готов к выдаче»; `UC_WXUMYB` — «Передан на доставку»; `UC_0JH5M4` — «Доставлено»; `WON` — «Завершено»; `UC_BBJSFZ` — «Отменен покупателем»; `LOSE` — «Не успешно»; `UC_RH2DBY` — «Возврат средств». Это стадии сделок, не доказательство настроек сопоставления с заказами МойСклад.

В этом live-запросе фактическая выборка сущностей Bitrix24 ограничилась типом и количеством счетов. Значения записей, персональные данные, связи конкретных контактов/компаний/ответственных, товары и значения custom fields в отчёт не выводились.

## Опубликованное поведение HTMLStudio

- Разработчик документирует обмен «сделка ↔ заказ покупателя» и настройку соответствия стадии сделки статусу заказа; для включённых пар требуется соответствие «один к одному», а при нескольких воронках учитывается комбинация «направление + стадия». Это описание возможностей приложения. Часть текущих настроек портала — включённые направления и выбранные соответствия — прочитана в UI 30.09 и приведена ниже; полный набор направлений и причинность событий по-прежнему не установлены. Отдельный журнал одной пары показывает целевое направление обновления сделки в B24 (см. дополнение 29.09), но не доказывает триггер конкретных событий. [HTMLStudio: заказ](https://www.htmls.ru/learning/course/index.php?CHAPTER_ID=0485&COURSE_ID=5&LESSON_PATH=194.202.485), [статусы](https://www.htmls.ru/learning/course/index.php?CHAPTER_ID=0204&COURSE_ID=5&LESSON_PATH=194.202.485.204).
- Для счетов HTMLStudio документирует настраиваемое соответствие статусов Bitrix24 и МойСклад; в МойСклад статусы счетов по умолчанию не создаются. Документ не устанавливает тип счёта в данном портале и не показывает, какие пары статусов реально выбраны. [HTMLStudio: счёт](https://www.htmls.ru/learning/course/index.php?CHAPTER_ID=0487&COURSE_ID=5&LESSON_PATH=194.202.487), [статусы счета](https://www.htmls.ru/learning/course/index.php?COURSE_ID=5&LESSON_ID=205&LESSON_PATH=194.202.487.205).
- HTMLStudio описывает отдельные пользовательские поля Bitrix24 для хранения ID МойСклад у сделок и счетов, но не публикует их коды в конкретном портале. Дополнительные поля сопоставляются настройкой; системные поля передаются без неё. [HTMLStudio: ID объектов](https://www.htmls.ru/learning/course/index.php?COURSE_ID=5&LESSON_ID=200&LESSON_PATH=194.494.200), [поля заказа](https://www.htmls.ru/learning/course/index.php?CHAPTER_ID=0486&COURSE_ID=5&LESSON_PATH=194.202.485.486), [поля счета](https://www.htmls.ru/learning/course/index.php?COURSE_ID=5&LESSON_ID=488&LESSON_PATH=194.202.487.488).
- Документация HTMLStudio также описывает фильтрацию заказов МойСклад по подразделению и пользовательским полям и запись отказа в журнал. UI 30.09 показал одно условие фильтра для направления МойСклад → Битрикс24, отсутствие строк фильтра для обратного направления и выключенный контроль минимальной цены; это срез параметров, а не подтверждение фактического применения фильтра к каждому заказу. [HTMLStudio: дополнительные настройки обмена заказов](https://www.htmls.ru/learning/course/index.php?CHAPTER_ID=0490&COURSE_ID=5&LESSON_PATH=194.202.485.490).

## Live API МойСклад (28 сентября 2026)

Авторизованные GET-запросы к `/entity/customerorder/metadata`, `/entity/customerorder/metadata/attributes`, `/entity/invoiceout/metadata` и `/entity/invoiceout/metadata/attributes` с заголовками `Accept: */*` и `Accept-Encoding: gzip` вернули HTTP 200. В коллекции пользовательских атрибутов `customerorder` получено 66 элементов; коллекция `invoiceout` вернула 0 элементов. В ответах метаданных пользовательских атрибутов представлены `id`, `name` и `type`; полей `code` и `title` в этих элементах нет. Пустая коллекция пользовательских атрибутов счета не говорит об отсутствии стандартных полей документа. [МойСклад: JSON API 1.2](https://dev.moysklad.ru/doc/api/remap/1.2/).

### Дополнение: позиции и audit связанной цепочки (read-only, 2026-09-30)

Для точечной цепочки `customerorder` ↔ `invoiceout` ↔ deal ↔ smart invoice product-row endpoint Bitrix24 и позиции документов МойСклад вернули HTTP 200. В МойСклад заказ и счёт содержали по одной строке типа `product`; их ссылки `assortment` совпали, как и количества. В Bitrix24 строка сделки и smart invoice ссылается на один и тот же товар торгового каталога. У этого товара свойство `property108` точно совпало с ID ассортиментного объекта МойСклад из строк документов. Это подтверждает товарную пару только для этой строки/цепочки; названия товара и денежные значения не сохранялись. В проверке использованы [crm.item.productrow.list](https://apidocs.bitrix24.com/api-reference/crm/universal/product-rows/crm-item-productrow-list.html), [catalog.product.get](https://apidocs.bitrix24.com/api-reference/catalog/product/catalog-product-get.html) и позиции JSON API МойСклад.

Повторные `GET` аудита для этого заказа и счёта покупателя вернули соответственно 6 и 5 событий. В аудите заказа две строки имели `source=remap-1.2` и UID с префиксом `bx24.htmls`; в аудите счёта одна строка имела такой же source и префикс. В просмотренных audit records отсутствовало поле `application`. Payload/diff и полные UID не читались/не сохранялись. Эти метаданные согласуются с активностью API-интеграции, но сами по себе не идентифицируют приложение, не устанавливают изменённые поля и не доказывают, что именно эта пара строк вызвала UI-события HTMLStudio.

Ссылки ответственных в системах структурно заполнены, но для этого примера их прямое сопоставление не подтвердилось: B24 назначает разные учётные записи сделке и smart invoice, тогда как заказ и invoiceout имеют одного владельца МойСклад. При локальном сравнении отображаемых имён ни один из двух B24 пользователей не совпал с этим сотрудником; поле `employee.externalCode` также не содержало ID этих B24 пользователей. Имена и значения контактных данных в отчёт не включены. Это свидетельство о конкретной цепочке, а не утверждение, что общего mapping нет в настройках HTMLStudio.
