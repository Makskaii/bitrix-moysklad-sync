Для фактических рабочих полей склада и организации используйте `rest_entity` B24 `IBLOCK_ID=38` и `IBLOCK_ID=88` соответственно, а не `catalog.store.list` и не CRM-компании. `catalog.store.list` — отдельный API складского учёта Bitrix24; он не подтверждён как источник значений поля сделки, а складской учёт в новый сервис не включается. Подробные ограниченные результаты чтения рабочих списков приведены ниже.

Все перечисленные методы чтения описаны поставщиками API. Наличие метода не подтверждает доступность конкретного раздела в данном аккаунте, объём прав токена или существование соответствующей записи. Настраиваемые пары пользователей, организаций, складов, валют и значений нужны для связных документов согласно [Issue #1](https://github.com/Makskaii/bitrix-moysklad-sync/issues/1) и [разделу требований о настройках](../requirements.md).

## Проверка доступа к админке

Владелец портала подтвердил критерий доступа: сервер разрешает действия в админке только при `user.admin == true`, проверяя его для каждого действия; видимость пункта меню не является границей доступа. Предположение об ID отдела администраторов опровергнуто: отдельного отдела нет. Требование и [Issue #1](https://github.com/Makskaii/bitrix-moysklad-sync/issues/1) синхронизированы с выбранным критерием.

Официальный метод [`user.admin`](https://apidocs.bitrix24.ru/api-reference/common/users/user-admin.html) возвращает boolean о правах **текущего пользователя**. Документация описывает для облачной версии право менять настройки Bitrix24, а для коробочной — участие в группе администраторов. Профиль [`profile`](https://apidocs.bitrix24.ru/api-reference/common/users/profile.html) также содержит `ADMIN`, который документация считает совпадающим с результатом `user.admin`, но `profile` возвращает и другие данные пользователя. В портале владелец выбрал именно правило `user.admin == true`; это подтверждённое продуктовое условие, не вывод о равенстве данного флага какому-либо другому критерию членства.

Для проверки на каждом запросе к админке нужен токен пользователя, открывшего встроенное приложение. Общий сервисный вебхук через `user.current` определяет только владельца вебхука и не устанавливает личность посетителя. Осталась техническая проверка в приложении: получить пользовательский токен и подтвердить успешный `user.admin == true` для известного администратора, а также `false` для известного не-администратора; ошибка вызова не должна трактоваться как `true`. Статья Bitrix24 о [правах доступа CRM](https://helpdesk.bitrix24.ru/open/23240636/) подтверждает наличие предустановленной группы «Администраторы» в выборе групп для ролей CRM, но не заменяет проверку выбранного владельцем критерия.

Права МойСклад — отдельная тема: [`GET /context/employee`](https://dev.moysklad.ru/doc/api/remap/1.2/) возвращает права вызывающего сотрудника; [`GET /entity/group`](https://github.com/moysklad/remap-1.2-java-sdk/blob/master/docs/GroupsApi.md) относится к группам МойСклад. Документация [Vendor API](https://dev.moysklad.ru/doc/api/vendor/1.0/) приводит `permissions.admin.view == "ALL"` как признак администратора МойСклад; этот признак не определяет доступ к админке Bitrix24.

Для новой проверки применялись штатные транспортные параметры проекта: Bitrix24 POST с JSON, МойСклад GET с `Accept: application/json;charset=utf-8` и Bearer-аутентификацией. Способ доступа `user.admin` выбран и сверён с документацией; тест через пользовательские токены остаётся задачей интеграции. Коды списков дают кандидатные пары складов, но их использование документами и финальная карта остаются открытыми.

`requirements.md` не закрепляет универсальную карту кодов пользовательских полей склада или организации. По наблюдениям владельца действующее приложение HTMLStudio использует Bitrix24-справочник `rest_entity` с `IBLOCK_ID=38` для рабочего поля склада и `IBLOCK_ID=88` для организации. Источник значений этих полей — элементы списков (`lists.element.get`), а не стандартный складской API. `catalog.store.list` относится к складскому учёту Bitrix24 и не подтверждён как источник рабочего поля сделки; включать складской учёт в новый сервис нельзя. Общий список CRM-компаний (`entityTypeId=4`) также не является списком собственных организаций. Ограниченная сверка списков B24 и МойСклад выявила совпадение `CODE`/UUID у 23/23 складов и 8/8 организаций; это только кандидаты на ключ, пока не проверены ссылки в документах и глобальная уникальность.

В T02 описаны четыре ограниченно проверенные связанные пары документов, где заполненные значения склада и организации Bitrix24 имели `CODE`, совпадающий с UUID соответствующего объекта МойСклад. Это подтверждает такой `CODE` как кандидат ключа для этих наблюдений, но не глобальную уникальность или карту всех пар. Значения списков 38/88 прочитаны; нужно проверить использование всех элементов в документах и согласовать правила, прежде чем считать пары готовыми.

### Дополнение: повторная проверка рабочих полей и ссылок (2026-09-30)

Владелец портала уточнил, что действующее HTMLStudio приложение использует рабочие списки типа `rest_entity`: `IBLOCK_ID=38` — поле склада, `IBLOCK_ID=88` — поле организации. Эти пользовательские значения нельзя приравнивать к API складского учёта Bitrix24 (`catalog.store.list`); новый сервис не включает складской учёт. Поля самих документов и подтверждённые в T02 связанные примеры остаются отдельным evidence.

Ограниченный read-only `lists.element.get` с `IBLOCK_TYPE_ID=rest_entity`, выбором только `ID,CODE,NAME` и первой (полной для этих размеров) страницей вернул 24 элемента списка 38 и 8 элементов списка 88. Сверка кодов в памяти с текущими ID из справочников МойСклад нашла 23/23 совпадений для неархивных складов и 8/8 для неархивных организаций; в отчёт не включаются персональные имя/ID организации физлица. Это кандидаты на ключ `CODE = UUID`, не окончательная карта, решение о направлениях или подтверждение использования каждым документом. У списка 38 один элемент (`ID=48680`, «7_ПВЗ_Краснодар») не совпал с ID ни одного склада МойСклад.

Для поиска кандидатов сотрудников выполнен полный постраничный read-only `user.get` (только `ID,NAME,LAST_NAME,SECOND_NAME,EMAIL,ACTIVE`) и чтение 145 неархивных сотрудников МойСклад. B24 вернул 242 пользователя, 91 active и 151 inactive. Email и ФИО использовались только в памяти: точный нормализованный email дал 42 уникальных кандидата среди active B24 и 3 среди inactive; точное ФИО после trim/свёртки пробелов/lowercase — 32 уникальных кандидата среди active, 11 среди inactive и один неоднозначный случай среди inactive. Имена, email, ID и таблица пар не сохранялись. Это генерация кандидатов, а не доказательство тождества сотрудников, назначение ответственных в реальных документах или утверждённая карта.

Официальная документация [`user.admin`](https://apidocs.bitrix24.ru/api-reference/common/users/user-admin.html) проверена: метод возвращает boolean администратора для текущего пользователя; в облачном портале это право менять настройки Bitrix24 (`bitrix24_config`), в коробочной версии — членство в группе администраторов. Поскольку владелец подтвердил именно `user.admin == true`, группа/отдел не используется как подмена критерия. Способ проверки выбран: встроенное приложение получает токен текущего пользователя и сервер вызывает `user.admin` на нём; ошибка/неуспех не дают доступ. Локально доступен только сервисный вебхук, не пользовательский OAuth-токен посетителя, поэтому live-пара admin/non-admin требует проверки при интеграции, а не подмены токена вебхуком.
