# T04 — связанные справочники и доступ

Проверено 2026-09-28. Основание: [T04](https://github.com/Makskaii/bitrix-moysklad-sync/issues/5), [родительская спецификация](https://github.com/Makskaii/bitrix-moysklad-sync/issues/1), [требования проекта](../requirements.md). Это карта источников и точек проверки, а не утверждённые соответствия в рабочих аккаунтах.

## Что нужно сопоставить

| Категория | Bitrix24: источник кандидатов | МойСклад: источник кандидатов | Что ещё проверить на рабочих данных |
| --- | --- | --- | --- |
| Ответственные/пользователи | [`user.get`](https://apidocs.bitrix24.ru/api-reference/user/user-get.html): ID, имя, активность, подразделения. | [`GET /entity/employee`](https://github.com/moysklad/remap-1.2-java-sdk/blob/master/docs/EmployeesApi.md). | Реальных владельцев заказов/сделок, активность, возможных общих пользователей и пары ID. Совпадение ФИО само по себе не доказывает тождество. |
| Склады | [`catalog.store.list`](https://apidocs.bitrix24.ru/api-reference/catalog/store/catalog-store-list.html) предоставляет список складов, если они используются на портале. | [`GET /entity/store`](https://github.com/moysklad/remap-1.2-java-sdk/blob/master/docs/StoresApi.md). | Какие склады реально выбирает документ и действующее приложение; требуется ли вообще пара со складом Bitrix24. | Организации | [`crm.item.list`](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-list.html) с `entityTypeId=4` перечисляет CRM-компании; [`crm.requisite.list`](https://apidocs.bitrix24.ru/api-reference/crm/requisites/universal/crm-requisite-list.html) — их реквизиты. Не приравнивать контрагента к собственной организации. |
| Валюты | [`crm.currency.list`](https://apidocs.bitrix24.ru/api-reference/crm/currency/crm-currency-list.html): поле `CURRENCY` и прочие свойства. | [`GET /entity/currency`](https://github.com/moysklad/remap-1.2-java-sdk/blob/master/docs/CurrenciesApi.md). | Фактически используемые в документах валюты и их ID/код. Код может быть кандидатом для пары, но применение требует проверки на реальных документах. |
| Прочие значения | Конкретные поля и списки документов пока не утверждены [требованиями](../requirements.md). | Проверять только справочники, на которые реально ссылаются выбранные документы. | Составить отдельные соответствия значений после утверждения полей, обязательности и направлений; не выдумывать общий перечень. |

Все перечисленные методы чтения описаны поставщиками API. Наличие метода не подтверждает доступность конкретного раздела в данном аккаунте, объём прав токена или существование соответствующей записи. Настраиваемые пары пользователей, организаций, складов, валют и значений нужны для связных документов согласно [Issue #1](https://github.com/Makskaii/bitrix-moysklad-sync/issues/1) и [разделу требований о настройках](../requirements.md).

## Отдел администраторов и серверная проверка

Требование: только сотрудник отдела администраторов получает доступ **ко всей** админке; сервер проверяет право при каждом действии. Пункт меню не служит границей доступа. ID отдела оставлен на проверку при подключении ([Issue #1](https://github.com/Makskaii/bitrix-moysklad-sync/issues/1), [требования](../requirements.md)).

Проверяемый путь: прочитать список отделов через [`department.get`](https://apidocs.bitrix24.ru/api-reference/departments/department-get.html), определить точный ID нужного отдела по владельцу портала, затем для каждого запроса к админке установить пользователя через [`user.current`](https://apidocs.bitrix24.ru/api-reference/user/user-current.html) **с токеном этого пользователя** и проверить `ACTIVE` и наличие утверждённого ID в `UF_DEPARTMENT`. Документация `user.current` показывает `UF_DEPARTMENT` как массив ID. Запрос с общим сервисным вебхуком идентифицирует владельца вебхука и не доказывает личность посетителя админки; схема приёма и проверки пользовательского токена должна быть проверена при подключении приложения. При ошибке проверки или отсутствии отдела действие запрещается. Если бизнес-правило подразумевает также вложенные отделы, это надо отдельно утвердить: прямое членство и членство в подотделе различаются.

Отдел Bitrix24 не следует смешивать с отделами МойСклад: [`GET /entity/group`](https://github.com/moysklad/remap-1.2-java-sdk/blob/master/docs/GroupsApi.md) относится к группам МойСклад. Права вызывающего сотрудника МойСклад доступны через [`GET /context/employee`](https://dev.moysklad.ru/doc/api/remap/1.2/); права отдельных сотрудников — через [employee security API](https://github.com/moysklad/remap-1.2-java-sdk/blob/master/docs/EmployeesApi.md). Документация [Vendor API](https://dev.moysklad.ru/doc/api/vendor/1.0/) приводит `permissions.admin.view == "ALL"` как признак администратора МойСклад. Это отдельная проверка прав токена МойСклад, не правило доступа к админке Bitrix24. Успешные целевые GET-запросы должны подтвердить фактический доступ на чтение.

## Состояние проверки конкретных аккаунтов

### Документация

Ссылки в таблице выше подтверждают назначение методов и формат доступных полей, но сами по себе не доказывают фактическое содержимое аккаунтов. Для Bitrix24 документация указывает `UF_DEPARTMENT` как список ID подразделений; для МойСклад `context/employee` возвращает права текущего сотрудника. Фактический live-доступ чтения к перечисленным ресурсам подтверждён ответами 2026-09-28, за исключением того, что ответ Bitrix24 по складам и компаниям не был разобран до списка кандидатов.

### TBD / не установлено

- ID отдела администраторов: среди 24 отделов нет отдела с очевидным названием «Администраторы»; владельца портала о выборе отдела не спрашивали, membership сотрудника вне отдела не проверяли.
- Метаданные полей со связкой `code → title/название → type` для Bitrix24 и МойСклад не получены. Отдельные live-запросы за ними не повторялись после отказа auto-review на сетевой запрос; результаты уже выполненных ограниченных GET приведены выше.
- Не установлены соответствия пользователей, складов, организаций, валют и прочих значений; не проверены фактические ссылки в документах и использование справочников.
- Не проверен токен конкретного сотрудника приложения и отказ пользователя вне отдела. `user.current` с вебхуком проверяет только контекст владельца вебхука.

Таким образом, наличие доступных методов и право токена МойСклад на административный просмотр подтверждены, но критерии T04 по точному ID отдела, метаданным полей и проверенным парам справочников остаются открытыми. До получения этих данных не фиксировать карты соответствий и считать связанные настройки незаполненными согласно [требованиям](../requirements.md).
