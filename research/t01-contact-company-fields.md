# T01 — поля и ключи контактов и компаний

Статус на 28.09.2026: схема публичных API и требования проекта подтверждены; метаданные Bitrix24 получены живым read-only API. Ограниченная выборка и сведения МоегоСклада остаются неполными, поэтому критерии [T01](https://github.com/Makskaii/bitrix-moysklad-sync/issues/2) по реальным совпадениям, конфликтам и приоритетам **не закрыты**. Родительская [спецификация #1](https://github.com/Makskaii/bitrix-moysklad-sync/issues/1) требует жёсткие пары по ID, но оставляет правила подбора на отдельное обследование.

## Подтверждено документацией API

| Сущность | Поля и типы, значимые для T01 | Источник |
| --- | --- | --- |
| Bitrix24, контакт | `ID` — integer; `NAME`, `SECOND_NAME`, `LAST_NAME` — string; `PHONE`, `EMAIL` — множественные `crm_multifield`; `COMPANY_ID` — основная компания; `COMPANY_IDS` — множественная связь, но для чтения полного списка компаний нужен отдельный `crm.contact.company.items.get`; `ORIGINATOR_ID`, `ORIGIN_ID`, `ORIGIN_VERSION` — строки для связи с внешним источником; `UF_...` — пользовательские поля с составом, зависящим от портала. | [crm.contact.fields](https://apidocs.bitrix24.ru/api-reference/crm/contacts/crm-contact-fields.html) |
| Bitrix24, компания | `ID` — integer; `TITLE` — string; `PHONE`, `EMAIL` — множественные `crm_multifield`; `CONTACT_ID` — множественная связь; `ORIGINATOR_ID`, `ORIGIN_ID`, `ORIGIN_VERSION` — строки; `UF_...` — поля портала. | [crm.company.fields](https://apidocs.bitrix24.ru/api-reference/crm/companies/crm-company-fields.html) |
| МойСклад, контрагент | `id` — UUID; `syncId` — UUID, отдельное поле с запретом изменения после заполнения; `code`, `externalCode`, `name`, `phone`, `email` — строки; `companyType` — enum; `contactpersons` — связанная коллекция; `attributes` — дополнительные поля. Для `companyType` документированы `legal`, `entrepreneur`, `individual` и региональные варианты. | [JSON API 1.2: контрагент](https://github.com/moysklad/api-remap-1.2-doc/blob/master/md/dictionaries/_counterparty.md) |
| МойСклад, контактное лицо контрагента | `id` — UUID; `agent` — ссылка на контрагента; `name`, `email`, `phone`, `externalCode` — строки. Контактное лицо адресуется через `/entity/counterparty/{id}/contactpersons/{contactPersonId}`. | [JSON API 1.2: контактные лица](https://github.com/moysklad/api-remap-1.2-doc/blob/master/md/dictionaries/_counterparty.md) |

Bitrix24 предоставляет `crm.contact.fields`/`crm.company.fields` для описания штатных и доступных `UF_...` полей, а `crm.contact.userfield.list`/`crm.company.userfield.list` — для настроек пользовательских полей, в частности `FIELD_NAME`, `USER_TYPE_ID` и признаков множественности. Это способы собрать каталог, но публичная документация не показывает состав конкретного портала. Источники: [контакты](https://apidocs.bitrix24.ru/api-reference/crm/contacts/userfield/crm-contact-userfield-list.html), [компании](https://apidocs.bitrix24.ru/api-reference/crm/companies/userfields/crm-company-userfield-list.html).

У МоегоСклада контекстный `search` по контрагентам проверяет также поля их контактных лиц и допускает вхождение подстроки. Поэтому результат `search` нельзя принимать за доказанное точное совпадение или за идентификацию конкретного контактного лица: кандидата нужно читать и сравнивать явно. [Документация контрагента](https://github.com/moysklad/api-remap-1.2-doc/blob/master/md/dictionaries/_counterparty.md).

## Подтверждено живым API и данные проекта

В [requirements.md](../requirements.md) и [T01](https://github.com/Makskaii/bitrix-moysklad-sync/issues/2) перечислены коды Bitrix24: UUID контакта `UF_CRM_1719834658`, UUID компании `UF_CRM_1719834633`, отметка дубля контакта `UF_CRM_1789126649744`, компании `UF_CRM_1789126724375`. В issues #1/#2 это **проектные исходные данные**, а не ответы API. Их наличие на портале, тип, множественность, заполненность и фактические значения признаков дубля не подтверждены.

**Bitrix24 (28.09.2026):** точечные GET к `crm.contact.fields`, `crm.company.fields`, `crm.contact.userfield.list` и `crm.company.userfield.list` на рабочем портале завершились успешно. `ID` контакта/компании возвращается как `integer` с title `ID`; ключевые штатные поля контакта: `NAME` (`string`, `Имя`), `SECOND_NAME` (`string`, `Отчество`), `LAST_NAME` (`string`, `Фамилия`), `PHONE` (`crm_multifield`, `Телефон`), `EMAIL` (`crm_multifield`, `E-mail`), `COMPANY_ID` (`crm_company`, `Компания`), `COMPANY_IDS` (`crm_company`, multiple), `ORIGINATOR_ID` (`string`, `Внешний источник`), `ORIGIN_ID` (`string`, `Идентификатор элемента во внешнем источнике`), `ORIGIN_VERSION` (`string`, `Версия оригинала`). Для компании: `TITLE` (`string`, `Название компании`), `PHONE`, `EMAIL`, `CONTACT_ID` (`crm_contact`, multiple), и те же три строковых поля origin.

Все четыре запрошенных UF-кода присутствуют в ответах `*.fields`: `UF_CRM_1719834658` (контакт UUID), `UF_CRM_1789126649744` (контакт-дубль), `UF_CRM_1719834633` (компания UUID), `UF_CRM_1789126724375` (компания-дубль). У каждого API type `string`, `isMultiple=False`, `isReadOnly=False`; title в `*.fields` равен самому коду UF. В `*.userfield.list` у всех `USER_TYPE_ID=string`, `MULTIPLE=N`, `MANDATORY=N`; `LIST_COLUMN_LABEL` и `EDIT_FORM_LABEL` пусты. Это означает, что API не предоставил человекочитаемый title этих UF-полей; называть их «UUID» и «дубль» можно только по требованиям проекта, не по заголовку портала. Значения полей не выгружались, поэтому фактические форматы и смысл признаков пока не подтверждены.

**МойСклад (наблюдения API от 28.09.2026):** официальный пример GET в [документации JSON API 1.2](https://dev.moysklad.ru/doc/api/remap/1.2/) использует `Accept-Encoding: gzip`. GET `/entity/counterparty/metadata` с `Accept-Encoding: gzip` и `Accept: */*` вернул HTTP `200`; верхнеуровневые ключи ответа: `meta`, `attributes`, `tags`, `createShared`. `attributes` в этом ответе — объект с ключом `meta`, а не список определений. GET `/entity/counterparty/metadata/attributes` вернул HTTP `200`, `count=5`, `size=5`, `limit=1000`, `offset=0`. В ответе доступны такие определения; `code` и `title` у всех пяти равны `null`:

| ID | `name` | `type` |
| --- | --- | --- |
| `056252d2-d4db-11e4-af04-002590a32f46` | Ответственный | `employee` |
| `4afe4ef0-f85f-11f0-0a80-1b2e0010264c` | Поставщик | `boolean` |
| `fbc1bec6-7172-11f1-0a80-026b00118443` | АдресГеокодирования | `string` |
| `0e62d64f-73b1-11f1-0a80-1522007d477f` | tgid | `string` |
| `4a13da84-73b1-11f1-0a80-1787007e90c7` | maxid | `string` |

GET `/entity/counterparty?limit=1` без `fields` и с теми же заголовками вернул HTTP `200`. В ответе были штатные ключи контрагента, в том числе `contactpersons`; ключ `attributes` у этой записи отсутствовал. Значения записи и вложенные значения контактных лиц не сохранялись. Прежний HTTP `412` относился к запросу `/entity/counterparty?limit=10&fields=...`; перечень `fields` для него не подтверждён как допустимый. Поэтому вывод о невозможности GET или необходимости исправлять поля по одному не следует из наблюдения: запрос без `fields` успешен. Ранее отмечавшиеся ошибки `400`/`415` не воспроизведены с `Accept-Encoding: gzip` и `Accept: */*`; эти заголовки сопровождали успешные GET выше. Это ограниченные наблюдения API, а не полная выгрузка контрагентов или контактных лиц.

**Ограничения проверки:** выборка записей Bitrix24 и полная либо репрезентативная выборка контрагентов/contactpersons МойСклада не получены; просмотрена только одна запись без сохранения значений. Поэтому проверка `UF` против `id`, `syncId`, `externalCode`, `code`, exact/normalized имени, телефона и email, а также статистика пустых значений, дублей и конфликтов не выполнена. Пары не создавались. Секреты и PII не записывались.

**Документировано:** схема и поведение методов описаны в официальных справках Bitrix24 [crm.contact.fields](https://apidocs.bitrix24.ru/api-reference/crm/contacts/crm-contact-fields.html), [crm.company.fields](https://apidocs.bitrix24.ru/api-reference/crm/companies/crm-company-fields.html), [crm.contact.userfield.list](https://apidocs.bitrix24.ru/api-reference/crm/contacts/userfield/crm-contact-userfield-list.html), [crm.company.userfield.list](https://apidocs.bitrix24.ru/api-reference/crm/companies/userfields/crm-company-userfield-list.html) и в [официальной документации МойСклад JSON API 1.2](https://dev.moysklad.ru/doc/api/remap/1.2/). Issues #1/#2 подтверждают требования проекта, но не фактические данные аккаунтов.

Без ограниченной выборки нельзя утверждать уникальность ключей или выбирать приоритеты. PII и секреты в отчёт не включались.

## Что нужно для закрытия T01

1. Получить ограниченную выборку МойСклад для проверки `contactpersons` и их полей; допустимый способ чтения контактных лиц отдельно не установлен. Каталог метаданных атрибутов контрагента уже получен, но соответствие этих полей реальным заполненным значениям не проверено. Сохранять только названия, типы и агрегаты без значений записей.
2. На ограниченной, воспроизводимой выборке проверить `UF_CRM_1719834658`/`UF_CRM_1719834633` против `counterparty.id`, `contactperson.id`, `syncId`, `externalCode` и других реально используемых кодов; отдельно проверить `ORIGINATOR_ID`/`ORIGIN_ID` и возможное поле «Внешний код» Bitrix24. Зафиксировать пустые значения, дубли внутри каждой системы, один-ко-многим, многие-к-одному и несовпадение типа сущности. До проверки не объявлять ни один ключ уникальным.
3. Для контактов сравнить ФИО с оговорённой нормализацией и обязательной проверкой телефона; email использовать как дополнительный признак. Для компаний проверить точное посимвольное имя и связи с контактами. Разделить сценарии `counterparty.companyType=individual`, юридических лиц и `contactperson` при компании. Итог — обезличенная матрица исходов и конфликтов, без публикации ФИО, телефонов, email или токенов.
4. Проверить фактические значения полей «Дубль». По [requirements.md](../requirements.md) исключается только связь с помеченной записью Bitrix24; непомеченный оригинал и документ не блокируются автоматически. Дать отдельную статистику исключённых записей и действующих оригиналов.
5. На основании выборки предложить и отдельно согласовать допустимые группы кандидатов, приоритеты ключей, правила при нескольких кандидатах и пороги сомнения. В рамках T01 пары не создавать и продуктивные записи не менять.

## Влияние на implementation tickets

- Обработчики контактов и компаний, первоначальная карта пар и защита от дубликатов зависят от проверенного каталога и приоритетов ключей. Пока нельзя зашивать соответствие «контакт Bitrix24 = физлицо МойСклад» или «контакт = contactperson»: [requirements.md](../requirements.md) оставляет выбор по реальным данным.
- Модель пар должна хранить идентификатор и тип записи МойСклад (`counterparty` либо контактное лицо с родительским контрагентом), основания сопоставления и исключение помеченной связи. Для одной записи МойСклад в пределах типа допускается одна активная пара; подтверждённая пара не пересчитывается при изменении имени. Это принятые требования [спецификации #1](https://github.com/Makskaii/bitrix-moysklad-sync/issues/1), а не вывод из API-документации.
- Автоматическое создание новых записей и включение обмена контактов/компаний должны ждать утверждённых результатов T01 и проверки готовности. Первоначальная инвентаризация сопоставляет старые записи и создаёт карты пар, но само сопоставление не создаёт записи во внешних системах и не переносит старые поля: [спецификация #1](https://github.com/Makskaii/bitrix-moysklad-sync/issues/1), [requirements.md](../requirements.md).
