# T01 — поля и ключи контактов и компаний

Статус на 29.09.2026: каталог полей и ограниченная обезличенная сверка завершены для T01. Все три критерия [T01](https://github.com/Makskaii/bitrix-moysklad-sync/issues/2) исследованы на описанных ниже выборках. Выводы о кандидатах — наблюдения и предложения для обсуждения; они не вводят новых продуктовых правил. Пары не создавались. Родительская [спецификация #1](https://github.com/Makskaii/bitrix-moysklad-sync/issues/1) требует жёсткие пары по ID и оставляет окончательные правила автоматического подбора на согласование.

Bitrix24 предоставляет `crm.contact.fields`/`crm.company.fields` для описания штатных и доступных `UF_...` полей, а `crm.contact.userfield.list`/`crm.company.userfield.list` — для настроек пользовательских полей, в частности `FIELD_NAME`, `USER_TYPE_ID` и признаков множественности. Это способы собрать каталог, но публичная документация не показывает состав конкретного портала. Источники: [контакты](https://apidocs.bitrix24.ru/api-reference/crm/contacts/userfield/crm-contact-userfield-list.html), [компании](https://apidocs.bitrix24.ru/api-reference/crm/companies/userfields/crm-company-userfield-list.html).

У МоегоСклада контекстный `search` по контрагентам проверяет также поля их контактных лиц и допускает вхождение подстроки. Поэтому результат `search` нельзя принимать за доказанное точное совпадение или за идентификацию конкретного контактного лица: кандидата нужно читать и сравнивать явно. [Документация контрагента](https://github.com/moysklad/api-remap-1.2-doc/blob/master/md/dictionaries/_counterparty.md).

## Подтверждено живым API и данные проекта

В [requirements.md](../requirements.md) и [T01](https://github.com/Makskaii/bitrix-moysklad-sync/issues/2) перечислены коды Bitrix24: UUID контакта `UF_CRM_1719834658`, UUID компании `UF_CRM_1719834633`, отметка дубля контакта `UF_CRM_1789126649744`, компании `UF_CRM_1789126724375`. В issues #1/#2 их назначение — **проектные исходные данные**, а не подписи API. Наличие полей и их типы были подтверждены метаданными портала 28.09.2026 (см. ниже); на ту дату заполненность записей ещё не проверялась. Выборка от 29.09.2026 подтвердила заполненность UUID и ограниченную статистику полей «Дубль».

**Bitrix24 (28.09.2026):** точечные GET к `crm.contact.fields`, `crm.company.fields`, `crm.contact.userfield.list` и `crm.company.userfield.list` на рабочем портале завершились успешно. `ID` контакта/компании возвращается как `integer` с title `ID`; ключевые штатные поля контакта: `NAME` (`string`, `Имя`), `SECOND_NAME` (`string`, `Отчество`), `LAST_NAME` (`string`, `Фамилия`), `PHONE` (`crm_multifield`, `Телефон`), `EMAIL` (`crm_multifield`, `E-mail`), `COMPANY_ID` (`crm_company`, `Компания`), `COMPANY_IDS` (`crm_company`, multiple), `ORIGINATOR_ID` (`string`, `Внешний источник`), `ORIGIN_ID` (`string`, `Идентификатор элемента во внешнем источнике`), `ORIGIN_VERSION` (`string`, `Версия оригинала`). Для компании: `TITLE` (`string`, `Название компании`), `PHONE`, `EMAIL`, `CONTACT_ID` (`crm_contact`), и те же три строковых поля origin. Полный список связей читается отдельным методом.

Все четыре запрошенных UF-кода присутствовали в ответах `*.fields` 28.09: `UF_CRM_1719834658` (контакт UUID), `UF_CRM_1789126649744` (контакт-дубль), `UF_CRM_1719834633` (компания UUID), `UF_CRM_1789126724375` (компания-дубль). У каждого API type `string`, `isMultiple=False`, `isReadOnly=False`; title в `*.fields` равен самому коду UF. В `*.userfield.list` у всех `USER_TYPE_ID=string`, `MULTIPLE=N`, `MANDATORY=N`; `LIST_COLUMN_LABEL` и `EDIT_FORM_LABEL` пусты. Поэтому «UUID» и «дубль» — назначение по требованиям проекта, а не человекочитаемые подписи портала. На 28.09 значения записей не запрашивались; формат UUID и заполненность UF подтверждены позднейшими выборками от 29.09 ниже. Значение поля «Дубль» и его охват проверены отдельно; принятая логика обработки приведена ниже по requirements.md.

**МойСклад (наблюдения API от 28.09.2026):** официальный пример GET в [документации JSON API 1.2](https://dev.moysklad.ru/doc/api/remap/1.2/) использует `Accept-Encoding: gzip`. GET `/entity/counterparty/metadata` с `Accept-Encoding: gzip` и `Accept: */*` вернул HTTP `200`; верхнеуровневые ключи ответа: `meta`, `attributes`, `tags`, `createShared`. `attributes` в этом ответе — объект с ключом `meta`, а не список определений. GET `/entity/counterparty/metadata/attributes` вернул HTTP `200`, `count=5`, `size=5`, `limit=1000`, `offset=0`. В ответе доступны такие определения; `code` и `title` у всех пяти равны `null`:

| ID | `name` | `type` |
| --- | --- | --- |
| `056252d2-d4db-11e4-af04-002590a32f46` | Ответственный | `employee` |
| `4afe4ef0-f85f-11f0-0a80-1b2e0010264c` | Поставщик | `boolean` |
| `fbc1bec6-7172-11f1-0a80-026b00118443` | АдресГеокодирования | `string` |
| `0e62d64f-73b1-11f1-0a80-1522007d477f` | tgid | `string` |
| `4a13da84-73b1-11f1-0a80-1787007e90c7` | maxid | `string` |

GET `/entity/counterparty?limit=1` без `fields` и с теми же заголовками вернул HTTP `200`. В ответе были штатные ключи контрагента, в том числе `contactpersons`; ключ `attributes` у этой записи отсутствовал. Значения записи и вложенные значения контактных лиц не сохранялись. Прежний HTTP `412` относился к запросу `/entity/counterparty?limit=10&fields=...`; перечень `fields` для него не подтверждён как допустимый. Поэтому вывод о невозможности GET или необходимости исправлять поля по одному не следует из наблюдения: запрос без `fields` успешен. Ранее отмечавшиеся ошибки `400`/`415` не воспроизведены с `Accept-Encoding: gzip` и `Accept: */*`; эти заголовки сопровождали успешные GET выше. Это исторический ограниченный снимок API от 28.09, а не полная выгрузка контрагентов или контактных лиц; позднейшие ограниченные страницы и contactpersons описаны ниже.

| МойСклад, metadata дополнительных полей | `type = boolean` (`Поставщик`); `type = employee` (`Ответственный`) | Реальные типы определений metadata, не значения атрибутов записей. |

Формы телефонных значений МойСклад в малой выборке включали цифры только и международный `+` с группирующей пунктуацией; цифры и необработанные номера отброшены. Маски/длины производны от значений текущих API-записей, но не раскрывают эти значения. Для поиска применялись только описанные выше операции нормализации.

### Результаты сопоставления кандидатов

Таблицы ниже разделяют старый XLSX и новые ограниченные API-проверки. Для нового межсистемного среза из первых и последних страниц B24 взяты позиции 1, 25 и 50 (по 6 контактов и компаний). Для каждого имени/названия искались контрагенты МойСклад по `search` (до 100 результатов на запрос; все 12 ответов были непагинированными). Число кандидатов считается по уникальным ID соответствующего типа: 0 — нет, 1 — ровно один, много — более одного. Точное имя означает буквальное совпадение строки; нормализованное — trim, свёртка пробелов, lowercase. Нормализованный телефон сравнивался по цифрам, с заменой 8 на 7 для 11 цифр; email — trim/lowercase. Это измерение конкретной выборки, не глобальная частота.

| Текущая живая API-проверка 29.09 | Контакты B24 (n=6) | Компании B24 (n=6) |
| --- | ---: | ---: |
| Кандидаты по точному имени / названию: 0 / 1 / много | 0 / 4 / 2 (макс. 6) | 0 / 4 / 2 (макс. 7) |
| Кандидаты по нормализованному имени / названию: 0 / 1 / много | 0 / 4 / 2 (макс. 6) | 0 / 4 / 2 (макс. 7) |
| Точное имя + точный телефон: 0 / 1 / много | 1 / 4 / 1 (макс. 3) | 6 / 0 / 0 |
| Нормализованное имя + нормализованный телефон: 0 / 1 / много | 0 / 5 / 1 (макс. 4) | 5 / 1 / 0 |
| Точное имя + точный email: 0 / 1 / много | 0 / 5 / 1 (макс. 4) | 5 / 0 / 1 (макс. 2) |
| Нормализованное имя + нормализованный email: 0 / 1 / много | 0 / 5 / 1 (макс. 4) | 5 / 0 / 1 (макс. 2) |
| Прямой UF UUID указывает на `counterparty.id` | 4/6 | 6/6 |
| Прямой UF UUID найден как `contactperson.id` в ограниченном поиске | 2/6 | — |

В контактном срезе имя само по себе оставляло неоднозначность для 2 из 6 записей (максимум 6 кандидатов); добавление телефона или email уменьшило, но не устранило её для одной записи (до 4 кандидатов). В срезе компаний имя оставляло 2/6 неоднозначными (до 7 кандидатов); телефон не дал кандидата для 5/6, а email оставил одну неоднозначную запись. Это реальные множественные ответы поиска, не созданные пары. Точечные GET по двум UUID, найденным в `contactpersons`, оба вернули HTTP 200 и тот же `id`, что и искомый UUID; `agent` совпал с parent-контрагентом из выборки. При этом у двух таких B24 контактов только одна из двух доступных связей `COMPANY_ID` совпала с parent-контрагентом — связь компании и тип UUID нельзя считать универсально установленными.

Отдельный старый низко-ID срез (первые 50 записей B24 на сущность, сопоставленные с XLSX 10.09 после дедупликации по UUID) дал совпадение UUID с уникальным `counterparty.id` 50/50 контактов и 50/50 компаний. Пять GET на тип подтвердили `id` для 5/5; `code` совпал с UUID в этих десяти точечных записях, `syncId` и `externalCode` — нет. `ORIGIN_ID` совпал с `externalCode` у 1/50 контактов и ни у одной компании. Совместные нормализованные имя+телефон дали 2/50 контактов и 0/50 компаний; имя+email — 1/50 и 0/50. Эти показатели принадлежат только старому XLSX-срезу, не текущему API и не должны сливаться с приведёнными выше выборочными результатами 29.09. Разница для контактов показывает, в частности, что UUID UF не всегда следует считать ID контрагента: в новом срезе два UUID адресовали contactperson.

Проверенные поля — лишь кандидаты для последующего проектирования/согласования, а не установленный этим исследованием приоритет или правило автоматики. Срез подтверждает, что следует различать `counterparty.id` и `contactperson.id`, а точные и нормализованные имя/название, телефон и email сами по себе не гарантируют уникального результата. Наблюдения не задают веса, пороги, создание пар или поведение при сомнительной паре.

**Принятая логика отметки «Дубль»:** согласно текущему `requirements.md`, отметка исключает из обмена связь только соответствующей записи B24; активная связь оригинала остаётся, а документ не блокируется автоматически. В этой исследовательской выборке проверено, что два UF-поля заполнены точным значением `Дубль` на найденных непустых записях; это сверка уже принятого требования с данными, не новое продуктовое согласование.

**Ограничения проверки:** выборки смещены и малы: каталог целиком не сканировался, только страницы/запросы, описанные выше. Для contactperson-кандидатов исследовались до 4 подходящих parent-коллекций на запрос и до 5 contactpersons в коллекции; один запрос имел более четырёх подходящих коллекций, поэтому подсчёт contactperson-кандидатов для него является нижней границей. Старый XLSX от 10.09 не содержит contactpersons и не является текущим API. Не измерены конфликты на всём портале, стабильность ключей за время, все связи компаний-контактов и распределение по `companyType`. Значения пользовательских атрибутов МойСклад не выгружались и не сопоставлялись с полями Bitrix24. Никакие пары не создавались, записи внешних систем не менялись, секреты и PII в отчёт не включались.

**Документировано:** схема и поведение методов описаны в официальных справках Bitrix24 [crm.contact.fields](https://apidocs.bitrix24.ru/api-reference/crm/contacts/crm-contact-fields.html), [crm.company.fields](https://apidocs.bitrix24.ru/api-reference/crm/companies/crm-company-fields.html), [crm.contact.userfield.list](https://apidocs.bitrix24.ru/api-reference/crm/contacts/userfield/crm-contact-userfield-list.html), [crm.company.userfield.list](https://apidocs.bitrix24.ru/api-reference/crm/companies/userfields/crm-company-userfield-list.html) и в [официальной документации МойСклад JSON API 1.2](https://dev.moysklad.ru/doc/api/remap/1.2/). Issues #1/#2 подтверждают требования проекта, но не фактические данные аккаунтов.

**Осталось проверить перед утверждением правил:** случайную/стратифицированную выборку, все конкурирующие UUID и дубли уже в полном каталоге, соответствие заполненных UF меткам дубля и существующей карте пар, contactpersons для разных `companyType`, все связи компаний/контактов, повторяемость кандидатов по имени/телефону/email, а также конфликты один-ко-многим и многие-к-одному на полном объёме. Эти ограничения не блокируют вывод T01 как разведочного отчёта, но не позволяют считать предложения автоматическими правилами.

Каталог полей, четыре UF-кода, фактическое значение непустых полей-дублей, типы и ограниченные примеры штатных и пользовательских полей обеих систем, UUID/`syncId`/коды, точные и нормализованные имена, телефоны/email и отдельный тип `contactperson` проверены в указанном объёме. ## Влияние на implementation tickets

- Обработчики контактов и компаний, первоначальная карта пар и защита от дубликатов зависят от проверенного каталога и приоритетов ключей. Пока нельзя зашивать соответствие «контакт Bitrix24 = физлицо МойСклад» или «контакт = contactperson»: [requirements.md](../requirements.md) оставляет выбор по реальным данным.
- Модель пар должна хранить идентификатор и тип записи МойСклад (`counterparty` либо контактное лицо с родительским контрагентом), основания сопоставления и исключение помеченной связи. Для одной записи МойСклад в пределах типа допускается одна активная пара; подтверждённая пара не пересчитывается при изменении имени. Это принятые требования [спецификации #1](https://github.com/Makskaii/bitrix-moysklad-sync/issues/1), а не вывод из API-документации.
- Автоматическое создание новых записей и включение обмена контактов/компаний должны ждать утверждённых результатов T01 и проверки готовности. Первоначальная инвентаризация сопоставляет старые записи и создаёт карты пар, но само сопоставление не создаёт записи во внешних системах и не переносит старые поля: [спецификация #1](https://github.com/Makskaii/bitrix-moysklad-sync/issues/1), [requirements.md](../requirements.md).
