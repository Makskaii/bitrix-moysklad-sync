## Summary

The official API models establish that the relevant concepts exist on both sides, but do not establish the current portal’s concrete ID pairs, full writability/round-trip behavior, or value transformations. Existing project research provides a bounded historical snapshot: product and service schema reads and deal/customerorder metadata reads from 2026-09-28; the service reference has a five-value `CODE`↔UUID observation; the payment-method attribute exists in customerorder metadata but its values were not inventoried. There is no safe, dedicated read-only live-account seam in the current application: the contact synchronizer combines reads and writes when it processes an event, and webhook endpoints only accept events. One bounded in-memory GET was permitted and performed separately; it did not verify the relevant attributes.

The accepted decisions can remain unchanged. The bounded GET was inconclusive. Technical closure still needs correctly parsed ID-only metadata/value reads and a carefully bounded read-only sample; until then, configured pair IDs, UOM conversion, all exact catalog price-type pairs, and reference value mappings remain TBD.

These are product decisions, not evidence that the present application/portal configuration implements the mappings.

## Primary-source facts checked

1. Bitrix24 catalog data types define catalog price records with `productId`, `catalogGroupId` (price-type ID), `price`, `currency`, and quantity bounds; price-type records carry ID/name/base/sort. The official `catalog.priceType.list` and `catalog.price.list` docs show the read endpoints. `catalog.measure.list` reads measurement units. Sources: [Bitrix24 catalog data types](https://apidocs.bitrix24.com/api-reference/catalog/data-types.html), [price type methods](https://apidocs.bitrix24.com/api-reference/catalog/price-type/index.html), [price methods](https://apidocs.bitrix24.com/api-reference/catalog/price/index.html), [measure methods](https://apidocs.bitrix24.com/api-reference/catalog/measure/index.html).
2. Bitrix24 deal product-row docs list `MEASURE_CODE`, `MEASURE_NAME`, `PRICE`, `QUANTITY`, tax and discount fields. This confirms row schema availability only; it does not define a cross-system mapping or conversions. Source: [crm.deal.productrows.set field reference](https://apidocs.bitrix24.com/api-reference/crm/deals/crm-deal-productrows-set.html).
3. Official MySklad SDK `Product` model lists the catalog fields and describes `packs` replacement/removal behavior; `Pack` has `uom` and `quantity`. MySklad document-position model also treats `pack` as a separate object. Sources: [Product model](https://github.com/moysklad/remap-1.2-java-sdk/blob/master/docs/Product.md), [Pack model](https://github.com/moysklad/remap-1.2-java-sdk/blob/master/docs/Pack.md), [DemandPosition model](https://github.com/moysklad/remap-1.2-java-sdk/blob/master/docs/DemandPosition.md). These are model definitions, not live account metadata.
4. MySklad JSON API documentation defines custom directory references as metadata links and exposes metadata/value resources using GET; a reference attribute’s value is object-like. This supports an ID/reference comparison workflow but does not establish actual customentity contents in this account. Source: [MySklad JSON API 1.2 — custom fields and metadata](https://dev.moysklad.ru/doc/api/remap/1.2/).

### Bounded live GET attempt (2026-10-06)

A GET to `entity/customerorder/metadata` returned HTTP success using the exact `Accept: application/json;charset=utf-8` header and built-in gzip decompression. The sanitized result contained top-level keys `meta`, `attributes`, `states`, `createShared`; the parsed `attributes` member contained one entry but no `name`, `id`, `type`, `required`, or `customEntityMeta.href` values under the expected shape. This is inconclusive and does not verify the service/payment-method attributes. A retry without gzip negotiation returned HTTP 415 and was not used as evidence. No customer/order records, PII, secrets, or value-list contents were requested or emitted; no POST/PUT/PATCH/DELETE was made. Investigate endpoint response shape in the next bounded technical-gate pass rather than treating this as metadata proof.

Historical live evidence in `research/t02-products-services.md` and `research/t03-deals-orders-invoices.md` remains useful but is dated 2026-09-28/29 and must not be presented as a fresh re-check. In particular, prior notes already record:
