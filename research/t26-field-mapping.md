# T26 — рабочая карта полей Bitrix24 ↔ МойСклад

Дата сводки: 2026-10-06. Статус: исследовательская карта с зафиксированными решениями владельца по части #26, включая Q26.11, Q26.20 и Q26.26–Q26.61; не является утверждённой runtime-конфигурацией сервиса.

## Как читать карту

В документе различаются четыре вида утверждений:

- **Схема** — код, подпись и тип подтверждены официальной API-документацией или live-метаданными портала/аккаунта.
- **Настроено в HTMLStudio** — пара прочитана в UI 2026-09-30. Это подтверждает сохранённую настройку направления B24 → МойСклад, но не заполненность, успешность или полноту фактической передачи.
- **Наблюдалось** — ограниченная безопасная выборка/журнал подтверждает только указанный факт. Это не универсальная карта и не основание для автоматического выбора.
- **TBD** — нет достаточных доказательств направления, преобразования, обязательности или эквивалентности; требуется указанный способ проверки и/или решение владельца.

**Статус согласования:** владелец подтвердил часть продуктовых решений #26; они отмечены ниже как решения, а не как технически проверенные возможности API. Остальные направления, техническая записываемость, преобразования, критичность и отдельные scope-вопросы остаются TBD. Это локальный исследовательский inventory, не утверждённая runtime-карта. AC5 остаётся pending; не считать его выполненным.

### Подтверждённые решения владельца по #26

| Вопрос | Принятое решение | Оставшаяся техническая проверка/граница |
| --- | --- | --- |
| Q26.1 — пары контактов | Существующие жёсткие пары не менять. | Q26.2 — несколько компаний | При нескольких компаниях использовать только явно выбранную основную компанию. Если primary не задана или её пара не найдена — ручная проверка, без угадывания. | Подтвердить источник primary в B24 и чтение полного списка связей для сценария. |
| Q26.3 — несколько телефонов/email | Передавать все значения в одно строковое поле МойСклад через разделитель. | Разделитель и обратное преобразование выбрать после технической проверки; конкретное значение не утверждено. |
| Q26.4 — ФИО, время и пары | ФИО собирать/разбирать автоматически согласно выбранному порядку частей; пользователь может вручную исправить ошибки в B24. Ручные правки считаются обычным изменением; переименование не меняет жёсткую пару. | Механизм защиты от эхо-событий/циклических записей требует технической проверки. |
| Q26.5 — порядок ФИО | `LAST_NAME NAME SECOND_NAME` («Фамилия Имя Отчество»), пропускать пустые части; существующие записи массово не переформатировать. | Проверить реализацию сборки/разбора, не менять старые значения массово. |
| Q26.6 — минимум данных нового контакта | Одно лишь полное имя не является основанием автоматически выбрать существующую пару. | Ранее допускалось standalone-создание контакта только с ФИО; это superseded для самостоятельного обмена Q26.17. Узкое создание клиента без телефона при обработке сделки/заказа описано Q26.17. |
| Q26.7 — заказ | Scope первой версии включает все 16 существующих HTMLStudio custom mappings и уже согласованные стандартные поля. | Для каждого поля отдельно подтвердить направление и преобразование, включая возможность записи; read-only/computed свойства не считать автоматически двусторонними. |
| Q26.8 / Q26.35 — номер заказа | MS `name` соответствует B24 `UF_CRM_1729757435964` («Номер заказа МС»); B24 `TITLE` — отдельное поле. Для новых заказов владелец выбрал штатную нумерацию МойСклад; полученный MS `name` сохранять в UF, но не использовать его как ключ пары. | Проверить, как Remap adapter получает штатный номер после создания; официальный API-материал не подтвердил omitted-name autocreation именно для Remap customerorder. |
| Q26.9 — очистка | Очистка необязательного синхронизируемого поля передаётся на другую сторону с приоритетом времени записи. | Состав функционально критичных полей остаётся TBD; поведение при очистке критичного поля определено Q26.11. |
| Q26.10 / Q26.60 — отдельное поле «Услуги» | Синхронизировать только reference value `UF_CRM_1766085949` ↔ customerorder `0ad997c8-8e75-11e3-1ec9-002590a28eca`; направление двустороннее, optional, одиночные изменения передавать, конфликт MS. Не создавать текстовую копию и не трактовать как product row. | Q26.20 handles absence/clear/unmapped optional value. Exact scoped value pairs/transforms/writability remain technical verification. |
| Q26.11 — очистка критичного поля | При очистке в МойСклад восстановить значение поля перед записью в БД: сначала последнее сохранённое успешно синхронизированное непустое значение именно этого поля МойСклад, иначе текущее значение соответствующего поля Bitrix24 в подтверждённой паре. Для очистки в Bitrix24 сохраняется Q77: восстановить из текущего значения МойСклад, а при отсутствии допустимого значения остановить обмен записи с причиной. Если оба источника пусты — не выдумывать значение и остановить обмен. | Новое пустое значение не должно затереть базу до восстановления. В случае ручной проверки зафиксировать случай, причину, поле, источник восстановления, прежнее и восстановленное значения с соблюдением действующей защиты данных. Состав критичных полей не расширяется этим решением; технические гарантии порядка записи и журналирования ещё проверить. |
| Q26.15 — критичность полного имени контакта | Составное непустое имя контакта `LAST_NAME NAME SECOND_NAME` ↔ МойСклад `name` критично; собирать из непустых частей. Очистку обрабатывать по Q26.11; если оба допустимых источника пусты, остановить обмен контакта и не выдумывать значение. | Отдельные части не обязательны по отдельности. |
| Q26.16 — критичность названия компании | B24 `TITLE` ↔ МойСклад `counterparty.name` критично; очистку обрабатывать по Q26.11. Если оба допустимых источника пусты, остановить обмен компании и не выдумывать значение. | Функциональная criticality и исключение из необязательных полей остаются только теми, что уже установлены решениями Q26.15–Q26.16. |
| Q26.17 — обязательный телефон и создание клиента для документа | Для standalone exchange контакт/компания без связи со сделкой или заказом должны иметь телефон; при обработке документа без телефона разрешено создать требуемого клиента. Подтверждённую пару не дублировать; отсутствие телефона само по себе не блокирует передачу документа. | Уточнено Q26.18: разрешение продолжается на дальнейшие самостоятельные изменения клиента, пока он связан со сделкой/заказом. Массовое копирование старых записей не разрешено; применение правила телефона к старым сопоставленным клиентам при первоначальной загрузке TBD. |
| Q26.18 — дальнейшие изменения связанного клиента без телефона | Пока сохранённая связь клиента со сделкой или заказом существует, разрешены дальнейшие самостоятельные изменения остальных полей без телефона. | Связь, удалённая из текущего сохранённого состояния, исключения не даёт. Закрытый статус документа сам по себе не прекращает исключение по Q26.19; проверить техническое обнаружение сохранённой связи и применение phone requirement при первоначальной обработке старых сопоставленных клиентов. |
| Q26.19 — сохранённая связь документа | Сохранённая связь контакта/компании со сделкой или заказом достаточна для исключения из требования телефона независимо от статуса документа, включая закрытый. Если сохранённая связь исчезла, прежняя история связи исключения не даёт. | Технически проверить распознавание текущей сохранённой связи; не продлевать исключение после её удаления. |
| Q26.20 — необязательное поле услуг | Поле-справочник сделки `UF_CRM_1766085949` необязательно для обмена сделки/заказа; отсутствие значения не блокирует передачу всего документа, очистка передаётся по общему правилу необязательных полей Q26.9. | Если выбранное значение не преобразуется из-за отсутствия пары, пропустить только это необязательное поле, передать остальные данные и создать случай ручной проверки. Поле не является товарной позицией; решение не определяет критичность остальных полей. |
| Q26.21 — criticality каталожного товара | Среди названия и цены в карточке товара критично только название; отсутствие цены не блокирует обмен карточки. | Не распространяется на цену товарной позиции документа, выбор оригинала/дубля или массовую копию старых записей. Критичность прочих связей/зависимостей отдельно не установлена. |
| Q26.22 — разрешение org/store/currency для заказа | Если source value задан — использовать его подтверждённую scoped pair; если пуст — использовать настроенный default; если source задан, но пары нет — блокировать весь заказ и журналировать причину для ручной проверки, без silent fallback. | Это отдельная critical dependency policy и не меняет Q26.20: выбранная услуга остаётся optional, а отсутствие/очистка не блокирует документ и обрабатывается по Q26.9. При проблеме преобразования выбранную услугу пропустить с review. Пользовательский screenshot 2026-10-01 подтверждает только default labels (`ООО «АЭРОСИСТЕМЫ»`, `1_Москва`, `руб`), не IDs. Отсутствующий/невалидный default при пустом source оставляет critical resolution failure; runtime API behavior не утверждается. |
| Q26.23 — явная цена позиции заказа | Цена каждой позиции должна быть явно задана; явный `0` допустим, отсутствие цены блокирует весь заказ, ноль не подставлять вместо отсутствующего значения. | Это цена строки документа, не карточки товара: optional catalog-card price по Q26.21 не меняется. Направление/преобразование/округление и техническое различение missing/null/0 ещё проверить. |
| Q26.26 — первое создание заказа по новой сделке | После вебхука создания новой сделки сначала искать существующую пару по утверждённым правилам. Если пары нет, создавать заказ при сопоставленной текущей стадии и готовности обязательных данных/зависимостей. Отдельная специальная стадия или флаг разрешения не нужны; при неготовности записать причину ожидания и повторить проверку при следующем изменении сделки. | Решение владельца для нашего сервиса, не вывод о runtime HTMLStudio. Официальный урок HTMLStudio [«Заказ покупателя»](https://www.htmls.ru/learning/course/index.php?CHAPTER_ID=0485&COURSE_ID=5&LESSON_PATH=194.202.485) требует настроить соответствие статусов при включении выгрузки сделок в заказы; урок [«Настройка статусов»](https://www.htmls.ru/learning/course/index.php?CHAPTER_ID=0204&COURSE_ID=5&LESSON_PATH=194.202.485.204) говорит, что участвуют выбранные пары, и описывает исходящий вебхук после изменения стадии роботом. Эти страницы не раскрывают точный триггер первого создания. Не меняет обновление существующих пар, обработку старых записей, cutoff создания новых записей, идемпотентность или retry временных ошибок. Готовность состава и правила отказа/возврата уточнены Q26.27–Q26.29. |
| Q26.27 — минимум состава при первом создании | Для первого создания заказа по новой сделке требуется хотя бы одна товарная позиция; все имеющиеся позиции должны пройти утверждённые проверки клиента, товара, цены и связей. Передавать только полный состав. | Если позиций нет или любая позиция не готова, заказ не создавать; записать причину ожидания и повторить readiness при следующем изменении сделки по Q26.26. Это не вводит правило удаления последней строки уже существующего связанного документа: применяются Q26.24–Q26.25. Это решение владельца, а не вывод из документации HTMLStudio. |

| Q26.29 — возврат новой сделки в работу | Для новой сделки, ожидающей первый заказ и не имеющей пары, после возврата в работу автоматически создать заказ без ручного подтверждения, как только текущая стадия сопоставлена и данные готовы по Q26.26–Q26.27. | Q26.32 — порядок выбора ответственного | При нескольких подходящих сопоставлениях выбирать первое отображаемое имя сотрудника целевой системы по алфавиту. ## Счета

В T03 наблюдалась одна цепочка `invoiceout → customerOrder → B24 deal → smart invoice entityTypeId=31`. В той цепочке `invoiceout.customerOrder` ссылался на заказ, `parentId2` — на сделку, а `xmlId` smart invoice совпал с ID `invoiceout`. Это единичное подтверждение существующей связи, не универсальное правило записи ID. Ограниченное live-чтение подтвердило одну запись на первой странице type31, не полный total. В UI HTMLStudio активны оба направления счетов, таблица дополнительных полей счета пуста, настроены только три статуса. Q26.12 выбирает type31 для будущего invoice этапа; Q26.45 откладывает его после первого запуска. Это не утверждает, что legacy type5 никогда не использовался.

Предыдущие T01–T04 подтверждают прочитанные ранее live-метаданные, интерфейсные настройки и ограниченные безопасные выборки. Не переносить выборочные counts/совпадения в утверждения о полноте или покрытии аккаунта; PII и значения полей в документ не записывались.

### Изменение и удаление товарных строк: API-возможности и границы

Наблюдение владельца («при изменении товарных позиций HTMLStudio удаляет и заново создаёт товары») пока не устанавливает, удаляются ли именно карточки товаров каталога или строки товара в документе, и не является доказательством конкретной последовательности API вызовов. Для проверки нужно отдельно сравнить до/после `productId` каталога и `id` строки заказа; наблюдение выполнять вручную на согласованном тестовом документе, не на production и без автоматического изменения.

Официальный Bitrix24 REST разделяет эти объекты: товарная строка привязана к документу через `ownerType`/`ownerId`, а ссылка на карточку каталога передаётся отдельным `productId`. Для точечного изменения доступен `crm.item.productrow.update` по ID строки; для удаления — `crm.item.productrow.delete`. Напротив, `crm.item.productrow.set` заменяет весь список строк документа переданным массивом, так что пропущенные строки будут удалены. Исторический `crm.deal.productrows.set` также документирует удаление отсутствующих строк, но помечен deprecated. См. [обзор product rows](https://apidocs.bitrix24.com/api-reference/crm/universal/product-rows/index.html), [update](https://apidocs.bitrix24.com/api-reference/crm/universal/product-rows/crm-item-productrow-update.html), [set](https://apidocs.bitrix24.com/api-reference/crm/universal/product-rows/crm-item-productrow-set.html) и [старый deal set](https://apidocs.bitrix24.com/api-reference/crm/deals/crm-deal-productrows-set.html).

Для МойСклад JSON API 1.2 официальная схема/SDK описывает чтение списка позиций заказа (`GET /entity/customerorder/{id}/positions`), изменение конкретной строки (`PUT .../{positionId}`), добавление (`POST .../positions`) и удаление (`DELETE .../{positionId}`). Следовательно, API имеет отдельный путь обновления по ID строки; этот факт сам по себе не доказывает, какой путь вызывает HTMLStudio. Источники: [официальный SDK MySklad Remap 1.2 — CustomerOrdersApi](https://github.com/moysklad/remap-1.2-java-sdk/blob/master/docs/CustomerOrdersApi.md) и [модели позиций CustomerOrder](https://github.com/moysklad/remap-1.2-java-sdk/tree/master/docs). Предыдущая заметка про замену полного массива относится к Vendor API update-provider и не используется здесь как доказательство семантики Remap 1.2.

Практические риски при выборе полной замены вместо адресного update: утрата/перевыдача ID строк, удаление пропущенных строк при неполном чтении или конкурентном изменении, нарушение пары с другой системой и повторные строки одного товара (карточный product ID не различает их). Если новый массив не сохраняет все исходные значения, могут потеряться скидки, НДС, единицы/упаковки, порядок и неподдержанные/ручные атрибуты; точный набор следует сверить по фактической схеме строки и round-trip на тестовом документе. Потеря продуктовой связи также может сделать строку несопоставимой; документация HTMLStudio сообщает, что при отсутствии `PRODUCT_ID` некоторые товарные строки не выгружаются, однако не раскрывает, как обновление сохраняет ID/metadata существующих строк. См. [ошибки HTMLStudio по выгрузке строк](https://www.htmls.ru/learning/course/index.php?COURSE_ID=5&LESSON_ID=524&LESSON_PATH=194.524).

Решение Q26.25: уже однозначно связанную строку обновлять адресно по её ID, новую строку добавлять отдельно; полную замену массива и delete+recreate для update не выбирать. Значения изменений передавать как итоговые абсолютные значения (не delta), чтобы повтор события не применял приращение повторно. Если кросс-системная пара строки не доказана, включая случай нескольких одинаковых `productId`, — ручная проверка, не эвристическое сопоставление и не молчаливое пересоздание. Удаление — только по Q26.24.

Это целевая продуктовая политика, не доказательство runtime-поддержки каждого поля или режима документа. До разработки подтвердить на двух системах отдельно: (1) стабильность ID строки после адресного изменения и повторного события, (2) права и поддержку нужных полей/обновления для фактических документов и статусов, (3) соответствие продукта/услуги и сохранность taxes/discounts/unit/custom attributes/order, (4) поведение на повторных одинаковых товарах, (5) защиту от полного-array overwrite и параллельных изменений. Bitrix24 и MySklad документируют адресные методы, но не гарантию HTMLStudio и не кросс-системное равенство row IDs. Поэтому сервис обязан сначала иметь проверенную пару row ID; без неё изменения направлять на ручную проверку. Q26.24 отдельно требует полного чтения перед удалением.

Уточнение Q26.19: сохранённая связь клиента со сделкой или заказом даёт исключение по телефону независимо от статуса документа, включая закрытый. Исключение прекращается, если сохранённая связь исчезла; только исторической связи недостаточно. Единственные оставшиеся TBD по этому правилу — техническое обнаружение сохранённой связи и применение требования телефона при первоначальной обработке старых сопоставленных клиентов.

Остальные критичные поля/связи ещё определить; подтвердить направления, разделитель для множественных PHONE/EMAIL, обратный разбор и защиту от эхо-обновлений. Технически проверить обнаружение сохранённой связи; отдельно проверить применение телефонного требования при первоначальной обработке старых сопоставленных клиентов. Жёсткие существующие пары остаются без изменений.
2. Компании: название `TITLE` ↔ `counterparty.name` критично по Q26.16; телефонное исключение при сохранённой связи и правила standalone обмена заданы Q26.17–Q26.19. Определить, критичны ли связь с контактом и другие поля компании; технически проверить обнаружение сохранённой связи и первоначальную обработку старых сопоставленных клиентов.
3. Заказы: для организации/склада/валюты policy resolution принята Q26.22; технически подтвердить IDs, scoped value maps, field directions/transforms и наличие/валидность UI defaults. Отдельно для остальных custom и согласованных стандартных полей проверить записываемость/направления/преобразования и определить дополнительную критичность (включая даты, суммы, скидки, адресный комментарий и `name`). Q26.11 действует для иных уже признанных critical fields.
4. Статусы/триггеры: scope Q26.13 — перенос наблюдённых пар стадий/статусов и action flags для функций, включённых в сервис; Q26.14 выключает все автоматические действия с отгрузками в v1. 6. Каталог и строки: выбрать бизнес-поля и направления; утвердить правила ключа `property108`↔`assortment.id` и используемые категории product/service/variant. По Q26.25 существующая строка обновляется адресно и итоговым абсолютным значением, новая добавляется отдельно; без проверенной пары row IDs — manual review, не delete+recreate/whole-list replacement. 7. Справочники/отдельное поле услуг: утвердить пары и направления employee/store/organization/currency/payment-method. Для услуги scope зафиксирован как значение справочника без текстовой копии и без product position; технически проверить направление и преобразование.
8. Для всех сущностей: определить функционально критичные поля и связи для готовности. Q26.9 задаёт обычную передачу очистки необязательного синхронизируемого поля по времени записи; Q26.11 задаёт восстановление очищенного критичного поля по источнику соответствующей стороны, порядок защиты сохранённого состояния, случай остановки и журналирование причины/источника/значений.
