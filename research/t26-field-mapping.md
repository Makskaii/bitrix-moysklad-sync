Дата сводки: 2026-10-01. Статус: исследовательская карта с зафиксированными решениями владельца по части #26; не является утверждённой runtime-конфигурацией сервиса.

## Как читать карту

В документе различаются четыре вида утверждений:

- **Схема** — код, подпись и тип подтверждены официальной API-документацией или live-метаданными портала/аккаунта.
- **Настроено в HTMLStudio** — пара прочитана в UI 2026-09-30. Это подтверждает сохранённую настройку направления B24 → МойСклад, но не заполненность, успешность или полноту фактической передачи.
- **Наблюдалось** — ограниченная безопасная выборка/журнал подтверждает только указанный факт. Это не универсальная карта и не основание для автоматического выбора.
- **TBD** — нет достаточных доказательств направления, преобразования, обязательности или эквивалентности; требуется указанный способ проверки и/или решение владельца.

**Статус согласования:** владелец подтвердил часть продуктовых решений #26; они отмечены ниже как решения, а не как технически проверенные возможности API. Остальные направления, техническая записываемость, преобразования, критичность и отдельные scope-вопросы остаются TBD. Это локальный исследовательский inventory, не утверждённая runtime-карта. ## Счета

## Происхождение схем и свежесть доказательств

Новое read-only чтение metadata API на 2026-09-30 (ответы схемы, без сохранения значений записей):

- Bitrix24 `crm.deal.userfield.list`: 17 полей; зафиксированы `FIELD_NAME`, API `EDIT_FORM_LABEL`/title, `USER_TYPE_ID`, множественность, `MANDATORY`, а для iblock element — `SETTINGS.IBLOCK_ID`. Все перечисленные UF single и API `MANDATORY=N`. Значения списков не запрашивались этим вызовом.
- Bitrix24 `crm.deal.fields`: схема 143 стандартных полей сделки; таблицы выше используют поля-кандидаты этой схемы.
- Bitrix24 `crm.item.fields` с `entityTypeId=31`, `useOriginalUfNames=Y`: схема 140 smart invoice полей; в таблице приведены только relevant candidates, а не все 140.
- Bitrix24 `crm.invoice.fields`: схема legacy invoice содержит 44 поля, включая `DATE_INSERT`, `DATE_UPDATE`, `STATUS_ID` и `UF_DEAL_ID`. Read-only `crm.invoice.list` с административным профилем и минимальным набором полей вернул `total=0` (проверка 2026-10-01). Документированный фильтр по `ID` был принят без ошибки, но из-за отсутствия совпадений корректность отбора по существующей записи не проверена. Это означает, что доступный этому профилю текущий набор legacy-записей пуст; это не доказывает отсутствие удалённых/исторических счетов или прежнее неиспользование типа. Дат, статусов и связей со сделками у текущих записей нет, поскольку записи не возвращены.
- Ограниченный `crm.item.list` для smart invoice `entityTypeId=31` вернул одну запись на первой странице (2026-10-01); total и полный исторический охват этой проверкой не устанавливались. Типы 31 и 5 не объединять в одно утверждение об использовании счетов.
- Официальная документация [crm.invoice.list](https://apidocs.bitrix24.com/api-reference/crm/outdated/invoice/crm-invoice-list.html) помечает метод legacy/deprecated, описывает фильтр/сортировку и указывает, что без фильтра возвращается доступный набор; для новых счетов Bitrix24 рекомендует универсальные методы и smart invoice. Семантика документации не снимает ограничения live-проверки и не даёт истории удалённых объектов.
- Bitrix24 `crm.item.productrow.fields`: схема из 22 полей приведена построчно выше. Документация API: [crm.item.productrow.fields](https://apidocs.bitrix24.com/api-reference/crm/universal/product-rows/crm-item-productrow-fields.html).

- МойСклад `GET /entity/customerorder/metadata` с `Accept: application/json;charset=utf-8`: HTTP 200; root metadata sections `meta`, `attributes`, `states`, `createShared`; schema содержит 66 customerorder custom attribute definitions. - МойСклад `GET /entity/invoiceout/metadata` с тем же Accept: HTTP 200; custom attributes schema count 0. Ноль относится к user-defined attributes в metadata, а не к стандартным свойствам `invoiceout`.
- МойСклад `GET /entity/product/metadata` с тем же Accept: HTTP 200; schema содержит 39 custom attribute definitions. Это не перечень заполненных значений.
- Сами стандартные schemas `CustomerOrder`, `InvoiceOut`, `CustomerOrderPosition`, `InvoiceOutPosition`, каталог контактов/компаний и product/service взяты из перечисленных официальных SDK/API-документов и прежних T01–T04, а не из новых live schema ответов. Особенно `shipmentAddressComment`: имя/настройка в T03, но тип отдельно не подтверждён.

Предыдущие T01–T04 подтверждают прочитанные ранее live-метаданные, интерфейсные настройки и ограниченные безопасные выборки. Не переносить выборочные counts/совпадения в утверждения о полноте или покрытии аккаунта; PII и значения полей в документ не записывались.

### Изменение и удаление товарных строк: API-возможности и границы

Наблюдение владельца («при изменении товарных позиций HTMLStudio удаляет и заново создаёт товары») пока не устанавливает, удаляются ли именно карточки товаров каталога или строки товара в документе, и не является доказательством конкретной последовательности API вызовов. Для проверки нужно отдельно сравнить до/после `productId` каталога и `id` строки заказа; наблюдение выполнять вручную на согласованном тестовом документе, не на production и без автоматического изменения.

Официальный Bitrix24 REST разделяет эти объекты: товарная строка привязана к документу через `ownerType`/`ownerId`, а ссылка на карточку каталога передаётся отдельным `productId`. Для точечного изменения доступен `crm.item.productrow.update` по ID строки; для удаления — `crm.item.productrow.delete`. Напротив, `crm.item.productrow.set` заменяет весь список строк документа переданным массивом, так что пропущенные строки будут удалены. Исторический `crm.deal.productrows.set` также документирует удаление отсутствующих строк, но помечен deprecated. См. [обзор product rows](https://apidocs.bitrix24.com/api-reference/crm/universal/product-rows/index.html), [update](https://apidocs.bitrix24.com/api-reference/crm/universal/product-rows/crm-item-productrow-update.html), [set](https://apidocs.bitrix24.com/api-reference/crm/universal/product-rows/crm-item-productrow-set.html) и [старый deal set](https://apidocs.bitrix24.com/api-reference/crm/deals/crm-deal-productrows-set.html).

Для МойСклад JSON API 1.2 официальная схема/SDK описывает чтение списка позиций заказа (`GET /entity/customerorder/{id}/positions`), изменение конкретной строки (`PUT .../{positionId}`), добавление (`POST .../positions`) и удаление (`DELETE .../{positionId}`). Следовательно, API имеет отдельный путь обновления по ID строки; этот факт сам по себе не доказывает, какой путь вызывает HTMLStudio. Источники: [официальный SDK MySklad Remap 1.2 — CustomerOrdersApi](https://github.com/moysklad/remap-1.2-java-sdk/blob/master/docs/CustomerOrdersApi.md) и [модели позиций CustomerOrder](https://github.com/moysklad/remap-1.2-java-sdk/tree/master/docs). Предыдущая заметка про замену полного массива относится к Vendor API update-provider и не используется здесь как доказательство семантики Remap 1.2.

Практические риски при выборе полной замены вместо адресного update: утрата/перевыдача ID строк, удаление пропущенных строк при неполном чтении или конкурентном изменении, нарушение пары с другой системой и повторные строки одного товара (карточный product ID не различает их). Если новый массив не сохраняет все исходные значения, могут потеряться скидки, НДС, единицы/упаковки, порядок и неподдержанные/ручные атрибуты; точный набор следует сверить по фактической схеме строки и round-trip на тестовом документе. Потеря продуктовой связи также может сделать строку несопоставимой; документация HTMLStudio сообщает, что при отсутствии `PRODUCT_ID` некоторые товарные строки не выгружаются, однако не раскрывает, как обновление сохраняет ID/metadata существующих строк. См. [ошибки HTMLStudio по выгрузке строк](https://www.htmls.ru/learning/course/index.php?COURSE_ID=5&LESSON_ID=524&LESSON_PATH=194.524).

Решение Q26.25: уже однозначно связанную строку обновлять адресно по её ID, новую строку добавлять отдельно; полную замену массива и delete+recreate для update не выбирать. Значения изменений передавать как итоговые абсолютные значения (не delta), чтобы повтор события не применял приращение повторно. Если кросс-системная пара строки не доказана, включая случай нескольких одинаковых `productId`, — ручная проверка, не эвристическое сопоставление и не молчаливое пересоздание. Удаление — только по Q26.24.

Это целевая продуктовая политика, не доказательство runtime-поддержки каждого поля или режима документа. До разработки подтвердить на двух системах отдельно: (1) стабильность ID строки после адресного изменения и повторного события, (2) права и поддержку нужных полей/обновления для фактических документов и статусов, (3) соответствие продукта/услуги и сохранность taxes/discounts/unit/custom attributes/order, (4) поведение на повторных одинаковых товарах, (5) защиту от полного-array overwrite и параллельных изменений. Bitrix24 и MySklad документируют адресные методы, но не гарантию HTMLStudio и не кросс-системное равенство row IDs. Поэтому сервис обязан сначала иметь проверенную пару row ID; без неё изменения направлять на ручную проверку. Q26.24 отдельно требует полного чтения перед удалением.

Уточнение Q26.19: сохранённая связь клиента со сделкой или заказом даёт исключение по телефону независимо от статуса документа, включая закрытый. Исключение прекращается, если сохранённая связь исчезла; только исторической связи недостаточно. Единственные оставшиеся TBD по этому правилу — техническое обнаружение сохранённой связи и применение требования телефона при первоначальной обработке старых сопоставленных клиентов.

Оставшиеся продуктовые решения владельца/эксперта, без которых карту нельзя объявить утверждённой:

1. Контакты: составное полное имя критично по Q26.15; телефон обязателен для самостоятельного sync только без сохранённой связи со сделкой/заказом (Q26.17–Q26.19), независимо от статуса связанного документа. Остальные критичные поля/связи ещё определить; подтвердить направления, разделитель для множественных PHONE/EMAIL, обратный разбор и защиту от эхо-обновлений. Технически проверить обнаружение сохранённой связи; отдельно проверить применение телефонного требования при первоначальной обработке старых сопоставленных клиентов. Жёсткие существующие пары остаются без изменений.
2. Компании: название `TITLE` ↔ `counterparty.name` критично по Q26.16; телефонное исключение при сохранённой связи и правила standalone обмена заданы Q26.17–Q26.19. Определить, критичны ли связь с контактом и другие поля компании; технически проверить обнаружение сохранённой связи и первоначальную обработку старых сопоставленных клиентов.
3. Заказы: для организации/склада/валюты policy resolution принята Q26.22; технически подтвердить IDs, scoped value maps, field directions/transforms и наличие/валидность UI defaults. Отдельно для остальных custom и согласованных стандартных полей проверить записываемость/направления/преобразования и определить дополнительную критичность (включая даты, суммы, скидки, адресный комментарий и `name`). Q26.11 действует для иных уже признанных critical fields.
4. Статусы/триггеры: scope Q26.13 — перенос наблюдённых пар стадий/статусов и action flags для функций, включённых в сервис; Q26.14 выключает все автоматические действия с отгрузками в v1. Технически получить account-specific `State` refs и подтвердить mapping для включённых status updates. Точную отгрузочную trigger-стадию отложить до будущего отдельного решения о включении функции; это больше не блокирует v1. Платёжные документы остаются вне v1.
5. Счета: scope решён Q26.12 — только smart invoice 31, без legacy type5. Ограниченная live-проверка и одна наблюдённая цепочка не доказывают историческую/удалённую историю type5, не устанавливают постоянное правило связи счёт↔заказ↔сделка и не подтверждают направления записи. Для включённого type31 остаются техническая проверка связи и направлений, определение критичных полей/связей и согласование функциональных статусов.
6. Каталог и строки: выбрать бизнес-поля и направления; утвердить правила ключа `property108`↔`assortment.id` и используемые категории product/service/variant. Цена строки явно обязательна по Q26.23 (ноль допустим, отсутствие блокирует заказ); цена карточки каталога отдельно optional по Q26.21. Q26.24 задаёт распространение удаления только при однозначной паре строки и подтверждении полного чтения, иначе manual review. По Q26.25 существующая строка обновляется адресно и итоговым абсолютным значением, новая добавляется отдельно; без проверенной пары row IDs — manual review, не delete+recreate/whole-list replacement. Ещё определить критичность связки product/service и количества, налогово-скидочных и unit/pack данных; технически подтвердить IDs, field support/writability и сохранение полей для in-place update. Сначала implementer подтверждает реальные mappings/transforms, не решая за владельца remaining functional criticality.
7. Справочники/отдельное поле услуг: утвердить пары и направления employee/store/organization/currency/payment-method. Для услуги scope зафиксирован как значение справочника без текстовой копии и без product position; технически проверить направление и преобразование.
8. Для всех сущностей: определить функционально критичные поля и связи для готовности; Q26.9 задаёт передачу очистки необязательного синхронизируемого поля по времени записи, а Q26.11 — блокировку всего элемента и журналирование прежнего значения при очистке критичного поля.
