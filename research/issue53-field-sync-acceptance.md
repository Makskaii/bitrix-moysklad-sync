# Issue #53 — configured client field-sync acceptance

This evidence note distinguishes the direct client-field surface currently supported by the client gateway from requisite/bank/account child resources that require an explicit adapter and identity mapping. It does not claim every Bitrix24 or MySklad field is synchronized. Current #53 governs; the historical #26 decision is not a permanent exclusion.

### Child-resource adapter contract and remaining integration

The explicit API configuration is `childResourceBindings` in the versioned Field Settings JSON. Each binding contains exact company, requisite, counterparty IDs, explicit field-code pairs, and optional exact bank-detail/account IDs. The adapter does not call list/add endpoints and rejects missing or ambiguous pair bindings. It captures mapped values as a baseline before any write, consumes an event-pinned settings version, journals dry proposals, applies through resource-specific update routes, reads back exact child IDs/values, treats an uncertain update response as successful only if readback confirms it, returns a new comparison snapshot, and persists that snapshot with the pair sync state. Production requisite calls require `BITRIX24_ALLOWED_ORIGIN` to match the configured REST webhook origin; isolated fake origins are allowed only in the explicit test adapter option. Official Bitrix docs distinguish requisite and bank-detail get/update methods ([`crm.requisite.get`](https://apidocs.bitrix24.com/api-reference/crm/requisites/universal/crm-requisite-get.html), [`crm.requisite.update`](https://apidocs.bitrix24.com/api-reference/crm/requisites/universal/crm-requisite-update.html), [`crm.requisite.bankdetail.get`](https://apidocs.bitrix24.com/api-reference/crm/requisites/bank-detail/crm-requisite-bank-detail-get.html), [`crm.requisite.bankdetail.update`](https://apidocs.bitrix24.com/api-reference/crm/requisites/bank-detail/crm-requisite-bank-detail-update.html)); the official MySklad [Remap 1.2 API](https://dev.moysklad.ru/doc/api/remap/1.2/) exposes counterparty accounts as nested resources.

## Safety invariants for acceptance

- A saved company/contact pair is authoritative even when the two sides have differing INN; log the discrepancy, do not replace the pair.
- A fallback MySklad company with empty INN is not populated from Bitrix24 during fallback resolution.
- An occupied target or missing paired target fails safe; no automatic reassignment or speculative create is permitted.
- First observation captures current-state baseline without writes. Subsequent updates use the event-pinned field-settings version, compare against reconciled current state, journal dry proposals, read them back, and only advance state after exact field/value reconciliation.
- Provider failure remains retryable according to the existing retry contract; an echo of a journaled write is not a second semantic change.
- `0` and `''` are present values for direct copy; only `null`/missing values are absent.
