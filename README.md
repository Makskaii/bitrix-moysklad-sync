# Bitrix24 ↔ МойСклад

Приложение для событийного обмена клиентами, документами и товарами между Битрикс24 и МойСклад. Административный интерфейс открывается внутри Битрикс24. PostgreSQL хранит очередь событий, связи записей, версии настроек, результаты обработки и журнал действий.

Это приложение для конкретного внедрения, а не универсальный установщик интеграции. В частности, проверка прав администратора сейчас привязана в коде к `aerosystems.bitrix24.ru`. Для другого портала одной замены переменных окружения недостаточно: требуется адаптация проверки авторизации и проверка схем полей.

## Возможности и ограничения

| Объекты | Направления и условия |
| --- | --- |
| Компании и контакты | Битрикс24 ↔ МС; только включённые направления и настроенные поля, с проверкой связей и зависимостей |
| Сделки и заказы покупателей | Битрикс24 ↔ МС; выбранные стадии, ссылки на клиента, позиции и обязательные справочники |
| Счета | Смарт-счета Битрикс24 `entityTypeId=31` ↔ счета покупателям МС; требуется подтверждённая связь с заказом |
| Каталог товаров и модификаций | МС → Битрикс24; обратная запись каталога из Битрикс24 не поддерживается |

Наличие обработчика не означает, что обмен уже настроен или прошёл сквозную проверку на конкретном аккаунте. После установки нужно подтвердить доступ, справочники, сопоставления и результат реального тестового события. Не включайте все направления одновременно без проверки.

## Состав проекта

- `apps/api` — API и обработчики на NestJS/TypeScript.
- `apps/web` — административный интерфейс на React/Vite.
- `prisma` — схема PostgreSQL и последовательные миграции.
- `apps/api/test`, `apps/web/e2e` — автоматические проверки.
- `docs`, `research`, `requirements.md` — требования и технические спецификации. Датированные документы могут описывать прежнее состояние; настройки действующего экземпляра проверяйте отдельно.

## Требования к окружению

- Node.js 22 и npm с поддержкой workspaces, как в Dockerfile проекта.
- PostgreSQL: базовый Docker Compose использует PostgreSQL 17; для своего сервера совместимость проверяется до обновления.
- Доступ к API Битрикс24 и МойСклад с необходимыми правами.
- Публичный HTTPS-адрес с доверенным сертификатом для интерфейса и входящих событий.
- Для контейнерного запуска — Docker Compose с поддержкой синтаксиса используемых override-файлов, включая `!override` для preview.

## Переменные окружения

Секреты храните вне репозитория, например в `/etc/bitrix-moysklad-sync/runtime.env`, с ограниченными правами. Не публикуйте REST URL входящего вебхука Битрикс24: в нём содержится секрет. Примеры ниже содержат только заглушки.

| Переменная | Назначение |
| --- | --- |
| `DATABASE_URL` | PostgreSQL для `apply`, включая параметр `schema` |
| `SYNC_MODE` | Обязательное значение `apply` или `dry` |
| `DRY_DATABASE_URL` | Отдельная БД или схема для `dry`; не должна совпадать с `DATABASE_URL` |
| `PORT` | Порт API, по умолчанию `3000` |
| `API_BIND_HOST` | IP привязки API; по умолчанию `0.0.0.0`. За локальным reverse proxy используйте `127.0.0.1` |
| `BITRIX24_REST_BASE_URL` | HTTPS REST base URL настроенного входящего вебхука Битрикс24, с завершающим `/` |
| `BITRIX24_ALLOWED_ORIGIN` | Разрешённый origin портала, например `https://aerosystems.bitrix24.ru` |
| `BITRIX24_EVENT_APPLICATION_TOKEN` | Токен проверки **входящих событий** Битрикс24; это не OAuth access token пользователя и не универсальный токен приложения |
| `MOYSKLAD_API_BASE_URL` | `https://api.moysklad.ru/api/remap/1.2/` |
| `MOYSKLAD_API_TOKEN` | Токен доступа к API МойСклад |
| `MOYSKLAD_WEBHOOK_SECRET` | Секрет входящего URL вебхука МС |
| `LOG_DIRECTORY` | Каталог файлового журнала, по умолчанию `logs` относительно рабочего каталога |
| `SYNC_OPERATIONAL_RETENTION_DAYS` | Хранение операционных данных в `apply`: 1–365 дней, по умолчанию 30 |

`SYNC_STATE` встречается в Compose, но не заменяет сохранённый режим сервиса. Оператор управляет `OFF/PAUSE/ON` через приложение; при перезапуске используется состояние PostgreSQL и проверяется подтверждение восстановления.

### Пример файла окружения для обычного API

```dotenv
DATABASE_URL=postgresql://sync:CHANGE_ME@127.0.0.1:5432/bitrix_moysklad_sync?schema=public
SYNC_MODE=apply
PORT=3000
API_BIND_HOST=127.0.0.1
BITRIX24_REST_BASE_URL=https://aerosystems.bitrix24.ru/rest/USER_ID/WEBHOOK_SECRET/
BITRIX24_ALLOWED_ORIGIN=https://aerosystems.bitrix24.ru
BITRIX24_EVENT_APPLICATION_TOKEN=REPLACE_WITH_EVENT_TOKEN
MOYSKLAD_API_BASE_URL=https://api.moysklad.ru/api/remap/1.2/
MOYSKLAD_API_TOKEN=REPLACE_WITH_API_TOKEN
MOYSKLAD_WEBHOOK_SECRET=REPLACE_WITH_RANDOM_SECRET
LOG_DIRECTORY=/var/log/bitrix-moysklad-sync
SYNC_OPERATIONAL_RETENTION_DAYS=30
```

Не используйте эти заглушки в работающем экземпляре. Node.js не загружает `.env` автоматически в точке входа приложения: передавайте окружение через менеджер процессов, shell или `node --env-file`.

## Установка без Docker

### 1. Подготовка PostgreSQL

Создайте отдельную БД и роли. Роль миграций должна иметь права на изменение схемы; рабочей роли приложения нужны права на используемые таблицы и последовательности. Миграции выполняйте владельцем схемы либо выделенной ролью миграций. Приложение не требует постоянного доступа суперпользователя PostgreSQL.

Для новой БД нужны все миграции из репозитория. Для существующей БД предварительно сделайте резервную копию и проверьте историю миграций. Не применяйте `prisma migrate reset`, не редактируйте уже применённые миграции и их checksums.

### 2. Получение и сборка

```bash
git clone https://github.com/Makskaii/bitrix-moysklad-sync.git
cd bitrix-moysklad-sync
npm ci
npm run build
```

Корневая команда сборки генерирует Prisma Client, собирает API и интерфейс. Результаты: `dist/apps/api/src/main.js` и `apps/web/dist`. API умеет раздавать собранный интерфейс сам, отдельный web-сервис необязателен.

### 3. Миграции и запуск

Пример для Bash; файл окружения должен быть доверенным и доступным только обслуживающему персоналу:

```bash
set -a
. /etc/bitrix-moysklad-sync/runtime.env
set +a

# Для apply. Если рабочая роль не владеет схемой, выполните эту
# команду отдельно с DATABASE_URL выделенной роли миграций.
npx prisma migrate deploy --schema prisma/schema.prisma
node dist/apps/api/src/main.js
```

При `SYNC_MODE=dry` миграции нужно применять к `DRY_DATABASE_URL`, а не к рабочей БД:

```bash
DATABASE_URL="$DRY_DATABASE_URL" npx prisma migrate deploy --schema prisma/schema.prisma
node dist/apps/api/src/main.js
```

Для проверки из другого терминала:

```bash
curl --fail http://127.0.0.1:3000/health
```

Ожидаемый ответ: `{"status":"ok","database":"ok"}`. Это проверка доступности API и PostgreSQL, **не** подтверждение работоспособности обмена с провайдерами.

### 4. Постоянный запуск через systemd

Пример unit-файла `/etc/systemd/system/bitrix-moysklad-sync.service` для Linux; пути и пользователь условные:

```ini
[Unit]
Description=Bitrix24 MySklad synchronization
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=sync
Group=sync
WorkingDirectory=/opt/bitrix-moysklad-sync/current
EnvironmentFile=/etc/bitrix-moysklad-sync/runtime.env
ExecStart=/usr/bin/node /opt/bitrix-moysklad-sync/current/dist/apps/api/src/main.js
Restart=on-failure
RestartSec=5
UMask=0077

[Install]
WantedBy=multi-user.target
```

До запуска создайте пользователя, каталог журналов с правом записи и доступ к собранному релизу. Миграции выполняются отдельно, до запуска новой версии.

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now bitrix-moysklad-sync.service
sudo systemctl status bitrix-moysklad-sync.service
```

Это инструкция для своего развёртывания, а не команда на изменение действующего сервера.

## Docker Compose

Для локального ознакомления из корня репозитория:

```bash
docker compose up -d --build db api web
docker compose ps
docker compose logs --tail=100 api
```

Интерфейс: `http://localhost:5173`, API: `http://localhost:3000`. API-контейнер сам выполняет миграции выбранной БД перед запуском. Данные PostgreSQL хранятся в томе `postgres-data`.

**Базовый Compose не является готовой production-конфигурацией:**

- Пароль БД `local-only` предназначен только для локальной среды.
- Порты `3000` и `5173` опубликованы без привязки к loopback; ограничьте их доступность firewall/override-файлом.
- В секции `api.environment` базового файла не переданы `MOYSKLAD_API_BASE_URL`, `MOYSKLAD_API_TOKEN`, `LOG_DIRECTORY`. Добавьте их в свой override. Простого добавления переменной в `.env` недостаточно, если Compose не передаёт её контейнеру.
- Штатный web nginx проксирует `/api/` и `/health`, но не `/webhooks/` и не стартовый `POST /` Битрикс24. Публичный reverse proxy должен направлять эти запросы в API.
- Настройте HTTPS, резервное копирование БД и постоянное хранение журналов вне жизненного цикла контейнера.
- Не запускайте профили `test`/`events-test` на рабочей БД и не используйте локальный admin preview как production API.

Для остановки без удаления томов используйте `docker compose stop`. Команда `docker compose down -v` удаляет том БД — для обычного обслуживания она не нужна.

## Подключение Битрикс24 и МойСклад

1. Подготовьте права интеграции в обоих сервисах и заполните секреты окружения.
2. Настройте reverse proxy с доверенным TLS. В варианте с одним API направляйте в него весь публичный адрес, включая `GET /`, `POST /`, `/api/`, `/health`, `/webhooks/` и статические ресурсы. Не блокируйте iframe политикой `X-Frame-Options: DENY`; допустимые origin для `frame-ancestors` ограничьте своим порталом.
3. В настройках локального приложения Битрикс24 укажите публичный HTTPS-адрес интерфейса. Открывайте приложение внутри портала под администратором: UI получает пользовательскую авторизацию через `BX24.init/getAuth`. Прямое открытие страницы вне Битрикс24 не даёт административных прав.
4. Создайте или проверьте **свои** подписки событий. Приложение не регистрирует все необходимые подписки автоматически при обычном старте. Не изменяйте подписки сторонних интеграций.
5. Для событий Битрикс24 используйте `POST https://YOUR_HOST/webhooks/bitrix24`. Проверяется `auth.application_token` тела события; он должен соответствовать `BITRIX24_EVENT_APPLICATION_TOKEN`.
6. Для событий МС используйте `POST https://YOUR_HOST/webhooks/moysklad/SECRET`, где `SECRET` соответствует `MOYSKLAD_WEBHOOK_SECRET`. Скрывайте этот путь в публичных примерах и логах reverse proxy.
7. Подписывайте только нужные объекты и операции: компании/контакты, сделки, смарт-счета типа 31; со стороны МС — соответствующие контрагенты, документы и каталог. Учитывайте, что контактное лицо МС — вложенный объект контрагента: не считайте наличие отдельного события гарантированным.
8. Проверьте настоящую доставку: измените разрешённую тестовую запись в исходном сервисе и найдите соответствующее событие в очереди приложения. Ручной POST на приёмник проверяет только HTTP-маршрут, но не подписку провайдера.

Стартовый `POST /` возвращает публичную HTML-оболочку и не доверяет присланным токенам запуска. Административные API отдельно требуют `Authorization: Bearer <пользовательский токен Битрикс24>` и успешную проверку администратора. Значение `DOMAIN` в URL не является авторизацией.

## Первый запуск и настройка обмена

### Два независимых режима

- `SYNC_MODE=apply` разрешает реальные записи при выполнении остальных проверок.
- `SYNC_MODE=dry` использует отдельную БД и журнал предполагаемых изменений вместо обычной внешней записи. Это не заменяет последующий реальный тест.

Режим сервиса хранится в PostgreSQL:

| Режим | Поведение |
| --- | --- |
| `OFF` | Приём и обработка обмена отключены. Пропущенные за этот период события автоматически не переигрываются |
| `PAUSE` | Входящие события сохраняются, обычная обработка приостановлена; продолжение требует явного включения |
| `ON` | Обработка разрешена только для включённых направлений и при пройденных проверках |

Переход в OFF не отменяет запрос, уже отправленный провайдеру. Подтверждение OFF ограничивает последующие операции; не интерпретируйте его как откат выполненных записей.

### Последовательность настройки

1. Убедитесь, что сервис OFF и подключён к правильной БД.
2. Проверьте раздел восстановления БД. Новая пустая БД не считается автоматически доверенной: требуется явное подтверждение начальной границы запуска и состояния связей. Для действительно нового внедрения отдельно зафиксируйте начальную UTC-границу и допустимый пустой baseline. После потери БД сначала восстановите и проверьте связи; не подтверждайте их восстановление формально.
3. Настройте поля и справочники: организацию, склад, валюту, единицы измерения, типы цен, каталог, выбранные стадии и необходимые зависимости. Используйте актуальные каталоги провайдеров и проверяйте точные ID.
4. Сохраните конфигурацию и проверьте версию. Активные несовместимые сопоставления отклоняются; преобразования должны быть явно настроены.
5. Проверьте направления в разделе управления обменом и выполните preflight. Устраните блокирующие причины до включения.
6. Включите только одно нужное направление, затем переведите сервис в ON с подтверждением.
7. Выполните ограниченный сквозной сценарий на новых тестовых записях. Проверьте не только статус события, но и внешний ID, связь и фактические значения на стороне получателя.

Проверка восстановления: `GET /api/admin/sync-mode/database-recovery`. Подтверждение: `POST /api/admin/sync-mode/database-recovery/confirm`; контракт описан в [спецификации восстановления](docs/database-loss-recovery.md). Не подставляйте вместо границы запуска `offSince` и не меняйте границу уже подтверждённого экземпляра ради повторного теста.

### Товары в сделке

В рабочем пользовательском сценарии добавляйте позиции через приложение **«Подбор товаров»**. Оно является отдельным приложением Битрикс24, а не частью данного репозитория.

Для текущего внедрения поле карточки каталога `property108` («Товары UUID») содержит **чистый `id` товара МС**. Это не `XML_ID` и не произвольный внешний код. При обработке позиции сначала используются сохранённая активная связь/явный alias; для несопоставленного товара проверяется точная карточка МС по UUID, затем сохраняется связь ID. Не найденный, некорректный, архивный или занятый UUID не заменяется поиском по названию. Проверка единиц, цены и остальных параметров строки выполняется отдельно.

При новом создании каталожной карточки из МС UUID также записывается в `property108`, если метаданные подтверждают допустимость записи. Завершённые старые операции не переписываются автоматически. Полный контракт: [идентификация товаров](docs/document-product-uuid-identity-2026-10-21.md).

## Ежедневная эксплуатация

- **Обзор:** состояние сервиса, доступность и направления.
- **Очередь и попытки:** источник, ID события, настройки принятого события, количество попыток и причина ошибки.
- **Связи записей / карта клиентов:** точные ID сопоставленных объектов. Не исправляйте неоднозначные связи прямым SQL.
- **Ручная проверка:** конфликты и неподтверждённые значения. Перед повтором проверьте, не была ли внешняя запись уже выполнена.
- **Журнал:** операции, ошибки и административные действия.

Ночная сверка использует часовой пояс `Europe/Moscow` и сохранённую историю активных интервалов. Она не является разрешением на массовый перенос всей истории или восстановление событий, потерянных вместе с БД.

Файловый журнал: `LOG_DIRECTORY/application.log`; ротация начинается при достижении 200 МиБ. Архивные файлы требуют контроля свободного места и отдельной политики хранения. В БД очистка запускается при старте и затем ежечасно: операционные данные — по retention (в dry 7 дней), закрытые случаи ручной проверки — 180 дней, административный аудит — 365 дней. Открытые случаи ручной проверки исключаются из удаления соответствующих событий.

Настройте резервное копирование PostgreSQL отдельно: само приложение не организует расписание резервных копий. Проверяйте восстановление на отдельной БД. Копии содержат рабочие данные и должны иметь ограниченный доступ.

## Обновление и откат

1. Зафиксируйте текущий commit, версии настроек, режим, направления и показатели очереди. Переведите обмен в OFF через приложение и дождитесь подтверждения.
2. Создайте резервную копию БД и защищённую копию конфигурации. Не выводите секреты в терминал или журнал.
3. Соберите **отдельный** каталог релиза из выбранного commit: `npm ci && npm run build`. Не пересобирайте файлы работающего процесса на месте.
4. Проверьте миграции и совместимость со старой версией. Выполните `prisma migrate deploy` ролью миграций. Историю и checksums уже применённых миграций не меняйте.
5. Переключите путь рабочего релиза и перезапустите сервис. Убедитесь, что он остался OFF.
6. Проверьте `/health`, загрузку UI, стартовый POST, отказ анонимного доступа к admin API и сохранность очереди/связей/настроек.
7. Сначала выполните ограниченный реальный сценарий; включение общего обмена — отдельное решение оператора.

Откат файлов приложения допустим только при совместимости со схемой БД. Автоматического downgrade миграций нет. При неопределённом результате внешней записи не сбрасывайте очередь, не создавайте второй объект и не восстанавливайте production-БД поверх работающей без отдельного плана согласования данных.

## Частые проблемы

| Симптом | Что проверить |
| --- | --- |
| `/health` не отвечает | Процесс, порт, IP привязки, доступность БД, миграции и права роли; при недоступной схеме API может не начать слушать порт |
| UI открыт, admin API возвращает 403 | Запуск внутри Битрикс24, пользовательский токен и права администратора; открытая HTML-страница сама прав не даёт |
| При запуске из Битрикс24 `Cannot POST /` | Что запрос попадает в API с обработчиком POST, а не только в статический nginx; что запущен нужный релиз |
| События не поступают | Реальную подписку провайдера, точный callback URL, TLS, секреты и OFF; наличие доступного HTTP-маршрута не доказывает подписку |
| Приёмник возвращает 401 | Соответствие event token Битрикс24 или секрета пути МС |
| Приёмник возвращает 410/503 | Режим OFF, незавершённое подтверждение восстановления, конфигурацию авторизации и причину ответа |
| Событие принято, но результата нет | Направление, preflight, выбранную стадию, границу запуска, зависимости клиента, очередь и ручную проверку |
| Позиция не перенесена | UUID/связь товара, единицу измерения, цену, налоги и причину пропуска конкретной строки |
| Не запускается dry | Наличие обеих DB URL и отличие целевой БД/схемы; миграции именно в dry-БД |

При расследовании сохраняйте ID события, исходного и целевого объектов, commit, версию настроек, время и безопасный код ошибки. Не прикладывайте токены, полные REST URL с ключами и необезличенные payload.
