# Локальный контур сервиса

Требуется Docker Desktop с Docker Compose. Запустить PostgreSQL, API и интерфейс можно одной командой из каталога проекта:

```sh
docker compose up --build
```

Интерфейс доступен по адресу http://localhost:5173 для проверки отображения, но административный экран открывается только внутри установленного приложения Bitrix24. API доступен на http://localhost:3000, а `GET /health` проверяет и API, и соединение с PostgreSQL. Prisma применяет миграцию при запуске API. Локальная БД использует только демонстрационные реквизиты и не подключается к Bitrix24 или МойСклад.

Проверка, что анонимные API-запросы не могут читать или менять административные данные:

```sh
docker compose --profile test run --build --rm smoke
```

Тест проверяет, что анонимные GET и POST административных данных получают отказ.

Проверка через браузер, что административный экран закрыт вне iframe Bitrix24:

```sh
docker compose --profile test run --build --rm browser-smoke
```

Интерфейс использует относительные `/api` и `/health` адреса. Nginx проксирует их на API внутри Compose, поэтому браузеру нужен только origin интерфейса.

## Локальный просмотр административного экрана

Для просмотра пробного административного экрана вне Bitrix24 используйте отдельный Compose-проект:

```sh
docker compose -p local-admin-preview -f docker-compose.yml -f docker-compose.preview.yml up --build
```

Откройте http://localhost:5174. В этом режиме сервер не проверяет права Bitrix24 для пробных административных действий; интерфейс показывает заметный баннер. Только веб-интерфейс опубликован на `127.0.0.1`; API доступен только веб-контейнеру во внутренней сети Compose. Сервисы используют отдельную базу проекта `local-admin-preview`. Обычный `docker compose up` по-прежнему требует администратора Bitrix24. Остановить просмотр можно командой `docker compose -p local-admin-preview -f docker-compose.yml -f docker-compose.preview.yml down`; база останется на месте.

### Ручная проверка административной навигации

Запустите локальный режим просмотра командой выше и откройте http://localhost:5174. В левом меню проверьте обзор, очередь и попытки, связи записей, ручную проверку, настройки, справочники, соответствия полей и логи. На обзоре сервис и режим должны отражать ответы локального API; количество очереди и пар должно быть помечено как недоступное, пока эти данные не подключены. Перейдите в «Соответствия полей»: редактор должен быть явно отмечен как находящийся в разработке. Кнопки в неподключённых разделах должны быть отключены.

Локальный режим просмотра использует отдельную базу и показывает заметный баннер о пропуске проверки прав. Для проверки реальной защиты откройте обычный интерфейс без Bitrix24: административная навигация не должна появиться. Сервер продолжает проверять право текущего пользователя Bitrix24 для каждого административного запроса.

Браузерная проверка локального режима с отдельной тестовой базой:

```sh
docker compose -p local-admin-preview-test -f docker-compose.yml -f docker-compose.preview.yml run --build --rm browser-smoke
```

Проверка нового интерфейса с preview-переменными, случайно переданными обычному API, использует отдельные локальные порты и базу:

```sh
docker compose -p local-admin-preview-off-test -f docker-compose.yml -f docker-compose.preview-off-test.yml --profile test run --build --rm browser-smoke
```

## Приём событий

При запуске задаётся `SYNC_MODE=apply|dry`; рабочий режим `on|pause|off` хранится в настройках сервиса. Для обычного Compose-запуска приём выключен (`off`); для вебхуков настраиваются отдельные секреты `BITRIX24_EVENT_APPLICATION_TOKEN` и `MOYSKLAD_WEBHOOK_SECRET`. Bitrix24 отправляет событие на `POST /webhooks/bitrix24`; токен проверяется по `auth.application_token`. URL вебхука МойСклад имеет вид `https://<host>/webhooks/moysklad/<secret>`. Приёмщик поддерживает тело с `events[]`, где элемент содержит `action` и ссылку `meta.href`; [руководство МойСклад](https://github.com/moysklad/workbook-api-doc/blob/master/pages/workbook/articles/webhooks.md) документирует `requestId` и повторное использование этого ID при повторной доставке.

Для настройки синхронизации реквизитов компании задайте `BITRIX24_REST_BASE_URL` с полным REST webhook URL и `BITRIX24_ALLOWED_ORIGIN` с точным HTTPS origin этого Bitrix24 портала (например, `https://portal.bitrix24.ru`). Сервис сравнивает origin до отправки webhook URL, содержащего секрет, и отклоняет несовпадение.

Событие сначала фиксируется в PostgreSQL, после чего endpoint отвечает `200`. Каждый элемент `events[]` МойСклад сохраняется отдельно; при наличии `requestId` ключ очереди использует ID, позицию события в batch и отпечаток тела. У вебхуков без документированного ID доставки каждый приём получает уникальный ключ: это at-least-once сохранение, чтобы не потерять позднее настоящее изменение с тем же телом; обработчики должны перечитывать текущее состояние и быть безопасны при повторной обработке. Во время `pause` события сохраняются до возобновления обработки; `off` отвечает `410` и ничего не сохраняет. В режиме `dry` приложение использует `DRY_DATABASE_URL` в отдельной PostgreSQL БД/схеме; запуск fail-closed, если dry и apply цели совпадают. Dry-предложения и состояние очереди остаются в изолированном тестовом контуре и не воспроизводятся в apply.

Для безопасной проверки подписок на сделки Bitrix24 и заказы покупателей МойСклад, включая матрицу событий, создание подписок и отчёт оператора, см. [инструкцию dry-проверки](docs/webhooks/deal-order-dry-check.md). Диагностический API `GET /api/admin/dry-webhooks` работает только в `SYNC_MODE=dry` и требует доступ администратора Bitrix24.

## Мониторинг, журналы и сроки хранения

Раздел «Мониторинг обмена» в админке показывает последние статусы очереди, открытые случаи ручной проверки, категории журналов `EVENT`, `SCHEDULED`, `ERROR` и `ADMIN`, а также историю вызовов внешних API. В очереди и журналах доступны только метаданные операции: полезная нагрузка вебхука, заголовки авторизации и тела API-запросов туда не копируются. Случай ручной проверки хранится отдельной записью без срока удаления; после 30/7 дней исходное событие может быть очищено, а запись случая остаётся доступной. Администратор может поставить доступное событие на повтор или отметить случай решённым.

Сервис запускает очистку при старте и затем раз в час. В `apply` история событий, вызовов API и событийные/плановые журналы хранится 30 дней. В `dry` вся история в отдельной базе очищается через 7 дней. Незакрытые случаи ручной проверки сохраняются до решения. Срок хранения журналов ошибок и действий администратора в `apply` пока не задан; их записи не удаляются этой политикой. Технический журнал API пишется в `logs/application.log` (или каталог из `LOG_DIRECTORY`); файл ротируется перед достижением 200 МБ.

Проверки мониторинга и ротации выполняются командой `npm run test:monitoring --workspace @sync/api`. PostgreSQL-сценарий очистки выполняется командой `npm run test:monitoring:postgres --workspace @sync/api` с `DATABASE_URL`, указывающим на изолированную схему теста, имя которой содержит `test` или `issue23`.

PostgreSQL-backed smoke-проверка использует изолированную схему `events_test` и два временных локальных токена. Пример запуска в PowerShell:

```powershell
$oldBitrixToken = $env:BITRIX24_EVENT_APPLICATION_TOKEN
$oldMoyskladSecret = $env:MOYSKLAD_WEBHOOK_SECRET
$env:BITRIX24_EVENT_APPLICATION_TOKEN = [guid]::NewGuid().ToString('N')
$env:MOYSKLAD_WEBHOOK_SECRET = [guid]::NewGuid().ToString('N')
try {
  docker compose -p t07-events --profile events-test run --build --rm events-smoke
} finally {
  if ($null -eq $oldBitrixToken) { Remove-Item Env:BITRIX24_EVENT_APPLICATION_TOKEN } else { $env:BITRIX24_EVENT_APPLICATION_TOKEN = $oldBitrixToken }
  if ($null -eq $oldMoyskladSecret) { Remove-Item Env:MOYSKLAD_WEBHOOK_SECRET } else { $env:MOYSKLAD_WEBHOOK_SECRET = $oldMoyskladSecret }
}
```

Профиль проверяет, что записи обеих систем доступны в PostgreSQL до ACK и повторные доставки не создают вторую запись. Контейнерный проект `t07-events` использует отдельный volume базы; тест оставляет его для повторного осмотра.
